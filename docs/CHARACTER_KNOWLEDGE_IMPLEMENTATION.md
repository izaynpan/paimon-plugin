# 角色知识库首版：使用与维护

2026-10-28：本地实现，角色集合默认关闭，未推送、部署或重启服务器。设计依据见 [角色知识库方案](CHARACTER_KNOWLEDGE_PLAN.md)。原有《日月全事》配置继续有效；角色资料需要额外构建并启用。

## 已实现范围

- 124 份显式列出的角色资料，七类文本转换为 13,066 个检索片段；另有九章《日月全事》1,297 个片段。JSON 是导入入口，Markdown 不重复入库。
- 139 条人物登记，正式名、经整理的别名、完整拼音和同音错字解析。登记数量不代表可玩角色人数，包含仅在剧情资料中的人物。
- 档案字段、故事与介绍、台词、人物评价、生日邮件和料理检索；人物与历史问题联合剧情资料。多人比较保留双方证据，共用现有字符预算。
- 旅行者共用引用和基准摘要校验、男版完整恢复；泛称旅行者的角色检索只取男女明确共用条目。原文对话保留，性别差异不自动推定。
- 人物评价按说话者与对象筛选，支持常见正向和“B在A眼中”“关于B，A怎么评价”等倒装，以及互评。复杂表达仍可能需要模型的一次本地补查。
- 生日邮件只按原文明确的主题、发件人、时间边界分封；显式日期进入标题，指定年份时排除其他已知年份，不推断缺失日期。
- 综合版本、旧快照兼容、原子切换、回滚、后台预热和同次回答固定版本；一次本地补查及既有联网限额保持。
- 初查/补查/模型请求/来源选择共享 requestId。内部记录全部合法选中来源，展示仍最多两条。

角色库不包含完整技能、命座效果、配装或培养数据。档案的武器类型、定位以及料理原文中的数值不能替代攻略依据。人物观点、页面编辑内容、编者推测均不自动升级为官方事实；所有结果保持 partial/unknown，由模型依据实际内容决定是否足够回答。

## 首次启用

以下命令在 `plugins/paimon-plugin` 目录执行，服务器需要在服务器自己的插件目录执行。只安装一个本地拼音依赖，不需要完整 Yunzai、Redis、QQ 环境或模型 API 来构建与离线验证。

```sh
# 锁定 pinyin-pro 版本；使用官方 npm registry，避免旧镜像证书问题
npm ci --ignore-scripts --registry=https://registry.npmjs.org

# 同时构建剧情与角色索引
node scripts/knowledge.js build --characters
node scripts/knowledge.js status
node scripts/knowledge.js query "钟璃喜欢什么食物？"
node scripts/knowledge.js query "达达利亚怎么评价丝柯克？"
node scripts/knowledge.js query "刻晴2024年的生日邮件"
```

`pinyin-pro` 的用法依据其 [官方仓库](https://github.com/zh-lx/pinyin-pro)，版本及完整性摘要固定在 `package-lock.json`。没有安装时，旧剧情模块仍可加载；角色索引准备会明确失败，不能静默当成无匹配。

在个人 `config/config.yaml` 的现有 knowledge 分组中合并：

```yaml
knowledge:
  enabled: true
  provider: genshin-lore
  lore: true
  characters: true
  topK: 6
  maxContextChars: 10000
  includeSources: false
```

`provider: genshin-lore` 保留旧名称，现可协调两类集合。`lore` 默认 true，`characters` 默认 false；升级代码不会自动启用角色集合。只查角色时可以关闭 lore；关闭 characters 后沿用旧剧情名称解析行为。

首次更新 JS 需重启。代码安装后集合开关和预算可热更新，变更集合会取消尚未发送的在途研究回复；已经发出的 API/协议消息无法撤回。首次开启前先构建，启用时预热，角色开关开启但快照不含角色时返回 `characters_not_built`，不伪装成资料缺失自动联网。

索引位于忽略的 `data/knowledge/`，不会随 Git 推送。此任务只在隔离的 `data/knowledge/character-validation/` 构建并验证，没有改个人配置或线上活动索引。

## 更新、版本与回滚

采集与发布分开，建议先更新到候选目录检查差异：

```sh
node scripts/collect-characters.js --out data/knowledge/character-candidate
```

检查报告无失败、预告排除正确、男女旅行者引用一致，审核后将资料更新到 `knowledge/characters/`。同一批旅行者必须一起更新，不能只换女版。来源字段、栏目和正文结构变化需先适配采集器，不靠忽略错误发布。

- `knowledge/character-sources.json` 明确列出文件、显示名、稳定人物 ID；和采集报告的输出名单必须一致。新增或删除人物需审核这份清单，避免把遗留旧文件或一次抓取失败当成正常变化。
- `knowledge/entities.json` 保存人物、资料入口和名称映射。新增人物补稳定 ID 和 profiles，检查别名冲突。人物名称变化时保留原 ID；跨页映射不是身份同一性的证明。
- 本次整理了可靠的旧剧情名称组；其余旧组仍只作剧情相关词扩展，审核说明在登记表的 review 字段。不自动复制指令或表情别名，不改变现有指令目标解析。
- `speakerMode: mixed` 标记混合说话者/身份页面。当前包括雷电将军及男女旅行者。雷电将军页未逐条标定人偶/影；他人评价中的同一宽泛标签也不作为精确人物方向的保证。此类资料可作带说明的文本证据，不强行完成说话者归属。
- 普通 JSON 指针指向原始条目；男版共用条目指向 `共用内容` 中的显式引用，并记录基准文件与条目标识。不能用恢复后的数组序号去定位差异文件。

候选构建、评估和发布：

```sh
node scripts/knowledge.js build --characters --no-activate
node scripts/evaluate-characters.js
node scripts/evaluate-knowledge.js
node tests/run-tests.js
node scripts/knowledge.js build --characters
```

首次需要 `--characters`。此后普通 `build` 保留活动快照已有集合，不会意外丢掉角色索引；`build --lore-only` 明确构建纯剧情版本。`query --lore-only "问题"` 可对比旧剧情结果。

```sh
node scripts/knowledge.js rollback
# 或指定既有修订
node scripts/knowledge.js rollback <revision>
```

一个综合快照包含剧情、角色、人物登记、解析版本及来源摘要；任一部分变化都会改变修订。构建和回滚均先验证可加载，再切换指针。角色解析规则改变时应维护 `CHARACTER_VERSION`；解析/版本不兼容不能强行接受旧数据。

运行时启动与配置变更会预热，并每 15 秒检查版本。准备新版本期间继续用完整旧版；同次回答初查和补查固定一个版本。因此发布后短时间仍见旧修订是正常现象，可查日志确认实际版本。预热失败保留可用旧版并报告；首次无可用索引则明确不可用。没有自动定时抓取网页。

## 名称解析的边界

正式名优先，其次经审核别名，再尝试同音匹配。原始问题保留，只规范检索词。示例：`刻情生日`、`钟璃喜欢什么食物`、`chongyun的生日`。完整拼音不带声调，重云/行秋的读音有人工覆盖；多音字仍可能需要补维护。

同音匹配只在人物话题中检查疑似姓名片段。候选不唯一时返回歧义，不默认选第一位。单字与泛称有边界限制，不能从“空气”“影响”“练琴”中认出空、影、琴。首字母如 `zl`、近音和任意编辑距离不支持。

名称表可加 `contextual: true` 限制常用称号，别名可以添加 `pinyin` 覆盖。`status` 会显示名称冲突；冲突是可诊断的歧义，不会按文件顺序覆盖。别名表未承诺涵盖所有玩家昵称。

## 证据与日志

证据仍在独立只读 user 数据块，不能改变人设、输出格式或调用工具。来源标题区分《日月全事》与角色资料；引用只接受实际提供的合法 ID。重复评价正文合并时保留其他来源位置，不把一段重复文本多次占用预算。

- `knowledge_lookup`：requestId、sessionId/sessionKey、initial/supplement、revision、状态、原因、snapshotIssue、实际提供的 sourceIds、截断标记。
- diagnostics：各集合候选数、提供片段数、字符数、查询耗时、规范人物 ID、exact/alias/pinyin，以及 context_budget/top_k/parent_limit 限制原因；歧义只记录候选 ID，不记录用户错字或原始问题。
- `knowledge_used`：全部合法选中 ID、对应集合及伪造 ID 的拒绝数量。前台最多显示两条不再限制内部统计。

初查/补查可能同时使用两类资料，因此“涉及某类资料的回复占比”可重叠。证据字符占比、选择出处占比都不能当成回答文字的实际贡献率，选择合法 ID 也不证明回答正确引用。模型请求/响应中的正文继续遵守日志开关。

## 验证记录与已知限制

新增 126 道人工指定查询及来源位置的角色检索题：86 道开发题、40 道预留题。预留题第一次独立运行 38/40，失败是单字人物参与评价时被名称过滤漏掉；修正后它们成为固定回归题，不能再把后续 40/40 描述为未见题成绩。最终 126/126 命中指定证据。剧情原有 100 题仍为 96/100，联合检索未丢失原先通过项。

测试另覆盖来源指针、男女引用、别名冲突、同音歧义、普通词误匹配、同作者续话、大写拼音、长对话说话者承接、评价方向、多人预算、年份邮件、旧快照兼容、正常构建保留集合、回滚、版本固定、开关取消及日志来源上限。完整插件离线测试 405/405 通过；无真实 QQ/API 调用。可复查的计数、修订及本机性能见 [验证报告](character-knowledge-validation.json)。

Windows 本地隔离实测（13,066 个角色片段 + 1,297 个剧情片段，综合 JSON 约 19.6 MiB）：构建并校验约 6.89 秒，独立新进程冷加载约 5.73 秒；126 题热查询 p50 约 6.38ms、p95 约 22.91ms。独立加载/查询进程 RSS 约 253 MiB、峰值约 462 MiB；构建校验进程峰值约 578 MiB，包含 worker 和序列化开销，非 Yunzai 全进程内存。冷加载超过原有 1.5 秒查询兜底，所以启动预热和更新时继续使用旧版是必需行为。正式部署前需观察服务器实际内存和预热耗时，不能把本机测量当服务器承诺。

首版交付核对：数据清单与引用对应上述来源指针测试；名称解析对应冲突/同音/普通词反例；联合检索对应角色126题及剧情原通过项逐题比较；聊天接入对应来源映射/完整日志/开关取消测试；更新维护对应综合修订、预热、构建保留集合、旧版本读取及回滚测试。阶段6的部署与真实回复观察不属于本次本地交付。

检索测试衡量证据是否进入上下文，不等于最终回答准确率。当前仍是词法召回、字段与人物规则，语义转述、非常规倒装、多人物复杂关系可能漏检；保留一次本地补查。没有向量服务、自动关系图谱、自动网页入库或战斗攻略扩展。
