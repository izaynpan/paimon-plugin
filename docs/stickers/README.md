## 标注依据与局限

逐张查看全部 53 组编号预览，共 848 张；优先处理文件名含派蒙的图片和序号最大的五组。描述和语义类型逐条填写，后续按受控词表展开结构化字段。不是仅从文件名猜情绪，也没有调用付费视觉 API。

对 12 张有歧义或需要细看文字的样本额外放大复看：`01-06`、`12-15`、`20-07`、`31-12`、`36-01`、`44-02`、`49-15`、`50-07`、`51-12`、`52-04`、`52-10`、`53-13`。此后再用原图尺寸九宫格逐张复看全部 49 张疑难图，45 张补充限制后列入候选，4 张明确排除。没有声称完成独立人工验收或模型实聊效果验证。

- `annotated`：首轮观察已完成，语义相对明确，可作为未来选择器的候选资料；不表示当前机器人已经会发送。
- `reviewed`：疑难图已经额外复看并补充语境限制；本轮 45 张。不表示独立人员验收或语义绝无歧义。
- `excluded`：复看后仍无法可靠判定身份或用途，本轮 4 张；`candidateEligible=false`，保留画面描述与排除理由。
- `needs_review`：身份冲突、主体/互动含糊或用途不明确，`candidateEligible=false`。未来接入时必须排除，不能仅按情绪绕过。
- 角色名主要来自文件名并结合外观核对，`confidence.character` 通常为 `medium`；没有对素材中的所有新名字做外部身份考证。
- 情绪和意图有解释空间。候选仍需与实际回复匹配；词表中的适用语境不能取代每图的 `visibleDescription`、`sceneConstraint` 和 `notes`。
- `visibleText=[]` 表示没有可靠的自然语言转写，不保证图片完全没有符号。问号、音符、睡眠字母和装饰图形通常在描述中记录；可辨的 `+1/+100/-100` 单独转写，不当真实机制数值。
- 文件名中的版本、目录标题和剧情名称只是素材组织信息，不据此确认官方来源、实际发布日期或版本事实。
- 把握程度是定性判断，不是测量的识别准确率。

特别注意：`44-02` 文件名是“奈芙尔 - 1.png”，画面却与同组菈乌玛形象相近。保留原文件名，将主体记作未知、菈乌玛记为候选，本轮已复核并排除，不自动更名。另排除 `19-01`（手举空白纸，缺身份和含义）、`36-01`（局部互动不足以确认主体和意图）、`43-06`（人物与屏幕组合语义不明）。

## 字段约定

完整字段见原方案第 5 节及 `catalog.json`。补充约定：

- `reviewKey`：人工检查编号，如 `01-06`。与库存快照的目录序号、组内位置绑定，不随文件系统枚举次序变化。
- `id`：由完整相对路径的 SHA-256 前 16 位派生，校验唯一。内容变化由独立 `contentHash` 检测；改名视为路径变化，需显式迁移，不能无提示复用旧语义。
- `characters`：图中主体/陪衬；`expressionSubject` 列出主要表达者。
- `associatedCharacters`：文件名关联但未作为主体出镜的人物。例如阿乔不等于基尼奇本人，月桂不等于瑶瑶本人。
- `characterIdentity`：保留文件名线索、形态、身份候选和判断依据；未知不强行填成具体角色。
- `paimonSelfExpression`：主体仅为派蒙的图片，可带陪衬动物；当前 14 张。
- `inLatestFiveAtAnnotation`：当前快照是否位于最大五组，当前为 49～53，共 80 张。未来运行时应重新计算，不永久依赖这份快照。
- `semanticProfile`：逐图选择的受控类型。通用情绪、意图、语气和基础语境由其展开；画面描述及备注逐图独立。复核项的适用语境由逐图决策替换，避免语境与词表规则合并。
- `candidateEligible`：候选资格，不是发送指令。初标候选也可能不适合当前回复。

## 原始观察格式与修改方式

每组文本每行：

```text
组内两位编号|语义类型|画面描述|备注（可省略）|可辨文字（可省略）
```

例：

```text
06|hungry|趴着睁眼，嘴角食物碎屑，口水垂到地上|已放大复看；更适合馋或等吃的玩笑，不当疲惫或悲伤
```

同一行的编号与 `inventory.json` 对应，不按重新排序后的文件列表重新分配。描述只写画面可见内容；剧情解释、可能含义或用途限制写到备注。

备注含“待复核”“待确认”“身份待”“表意有歧义”“含义不明确”“不能可靠转写”“文字待辨认”时，构建器会保守标为 `needs_review`；身份修正中 `identityUncertain:true` 也会阻止进入候选。此规则是当前离线资料工具的约定，不是运行时语义分类器。显式复核以 `review-decisions.json` 的 `reviewed` / `excluded` 为准，必须补实际描述、结论、原疑点及语境限制，并绑定原图摘要；不能为了增加候选数简单删除疑点。身份仍标为不确定的图片禁止设置为复核可用。

主体或关联关系修改 `character-overrides.json`；别名修改 `character-aliases.json`；通用语境规则修改 `profiles.txt`。不要直接修改生成的 `catalog.json` 或 `REVIEW.md`，否则下一次构建会覆盖，校验也会报告不一致。

## 本地重建与增量检查

在插件目录执行，不依赖 Yunzai、Redis、QQ、第三方 Node 包或 API：

```sh
node scripts/sticker-catalog.js build
node scripts/sticker-catalog.js validate
node scripts/sticker-catalog.js scan
```

- `build`：检查原图与库存一致，读取逐图记录和词表，生成索引、复核报告及本地预览。
- `validate`：检查编号/路径/图片摘要、标注覆盖率、语义类型和生成结果一致性。包含真实路径边界及精确文件名大小写检查。
- `scan`：只报告新增、内容变化、缺失图片，并保存 `data/sticker-review/inventory-changes.json`；不自动给新图赋情绪、不覆盖旧标签。

新增图片后先扫描差异，为新图生成新稳定 ID 和摘要，在对应组追加未使用位置（新增组从 1 开始），看图后再补记录。旧图内容变化须重新看图并更新摘要；有复核决策时还须重新复核并更新决策的摘要，不能只更新库存绕过旧决定；缺失或改名须人工核对来源和引用。只更新确有变化的库存记录，保留其余编号。增量扫描不自动完成这些人工步骤；库存与文件不一致时构建/校验会拒绝继续，避免旧标注悄悄套到新图。

`data/sticker-review/` 是可再生成的本地检查产物，已加入忽略规则。53 张总览及放大复核图是此次检查的本地产物；生成器负责重建筛选预览，不要求这些总览图存在。
