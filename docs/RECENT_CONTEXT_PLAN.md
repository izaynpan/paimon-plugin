# 近期会话衔接与搜索缓存方案

日期：2026-10-18。状态：已在本地实现并完成离线验证；以下保留设计依据，实际配置以 README 和代码为准。默认关闭，未修改个人配置、推送、部署或重启。

## 实现落点与已知边界

- `lib/recent-context.js`：限期问答、作者/消息命名空间、容量与候选选择；`lib/cache-file.js`：串行原子快照和损坏降级；`lib/quoted-message.js`：同范围安全单条原文读取。`paimon-runtime` 连接触发、引用预算、成功发送归档、条件撤销与重启生命周期，旧资料不进入 sessionBatches。
- `web-search.js`：有效 TTL 选择、公开工具缓存和带版本/凭证分区的证据快照；近期批次仅保存证据哈希引用，正文不混入聊天档案。公开结果与证据快照各 100 项硬上限。`prompt-builder` 以独立只读材料提供候选、原文或引用不可用状态。
- 引用协议已核对本地 OneBot 适配器的 `get_msg` 与发送回执，以及 [NapCat GetMsg 官方实现](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/action/msg/GetMsg.ts) 的字段；尚未在实际部署的 NapCat 版本上验证本插件新增链路。私聊协议未能证明 Bot 发出消息的收件人时拒绝使用，本地发送映射仍可读取。只接受结构化文字，CQ 字符串降级。
- 候选由引用对应问答、对应旧 session 开头、文本匹配、发言者和时间确定，不声称实现了实体识别或模型语义分类器。每批最终取最后明确引用对应的已取得原文，初始化等待期间新增的引用可能因共享预算/队列而不可用；不逐条追加查询和长等待。
- 只归档正常文字的实际成功片段，沉默、错误兜底、自动补话不归档。发送不返回消息 ID 时仍保存文字，不伪造 ID；多个 ID 无法明确分段映射时不建立该条引用映射。写入按成功片段及时更新有界快照，仍可能在突然断电时丢失未落盘部分。
- 热改关闭/撤白、原始时间过期、损坏降级、跨重启恢复、不恢复活跃计时器、原触发边界、引用超时/错误范围、有效证据跨 session 复用及过期重搜均有模拟离线测试。新增 26 项，完整离线测试 206/206 通过。语义效果、QQ 发收和真实 API 计费仍需联调；模拟响应不能证明实际模型总能正确续话。

## 1. 目标与默认选择

即使关闭长期记忆，用户隔一段时间再次呼唤派蒙，或另一位群友引用派蒙的回复继续问，也能在有限范围内知道此前讨论对象、个人条件和未解决问题。网页证据过期后可以重新查，不能因为网页过期而把提问主题一起丢掉。

建议近期上下文与搜索缓存统一配置为 **1 天（24 小时）**。保留原 90 秒活跃会话窗口：它决定何时接收无需呼唤的普通续话；24 小时只决定已接纳内容能保留多久，不代表连续监听/回应群聊 24 小时。超过活跃窗口仍须通过原昵称/@ 等规则重新触发。

用户补充了 Yunzai 每天定时重启的运行条件，因此将原“仅内存”设计改为 **内存缓存 + 本地文件持久化**，近期问答和公开搜索证据一起保存，启动时恢复未过期部分。Yunzai 进程重启/execve 会丢失 JavaScript 内存，即使宿主机、容器和 Redis 没重启也不能保住这些对象。不增加数据库、额外摘要 API 或后台搜索；现有调试日志不会被当作聊天历史自动回放。

## 2. 三类信息独立处理

| 类型 | 用途 | 建议保存方式 |
| --- | --- | --- |
| 近期聊天片段 | 弄清楚在讨论谁、谁有什么角色、还有什么问题 | 按群/私聊保存有限文本，24 小时过期 |
| 搜索证据 | 支撑当前事实、配队和版本结论 | 保留原 URL、日期、获取时间及摘录，最长 24 小时 |
| 长期用户记忆 | 个人稳定偏好、角色持有情况、长期约定 | 继续由原 memory 开关和评估流程控制 |

关闭 memory 时，近期片段仍可使用，但不会因为缓存命中而写个人记忆。开启 memory 时，沿用原评估机制；导入的旧片段、引用原文和网页内容不作为本轮新发言再次送去提取，不因反复衔接而重复记忆。当前用户新提供的个人信息仍可按原规则被评估。

## 3. 保留什么内容

首版采用带来源的原文片段，不要求模型另写一份概括：

- 原始用户文本、发言者、发生时间、群/私聊范围、会话与消息标识。
- 派蒙真正发送成功的文字。部分发送失败时仅保存成功部分，不保存未发出的候选答案。
- 对话先后顺序与已知的引用关系，使模型能从原文理解讨论对象、个人条件和未解决问题。没有明确依据的关系不得凭空生成。
- 对应搜索来源的标识、获取时间与版本元数据；聊天记录与网页正文分别存放。

容量建议：每个聊天最多 20 个已完成批次、合计 16,000 字符，全局最多 200 个聊天；超过任一容量可以提前淘汰，24 小时是最长保留期，不承诺完整保存全部讨论。保存时优先保留有正常回复的问答；合法沉默不额外归档为跨会话资料，自动补话不独立续期。仅来自原触发/白名单范围内的已接纳消息，不持续采集未触发的普通群消息。

上下文按群号/私聊用户隔离，不按 Bot 账号隔离，不把私聊带入群聊，也不串群。群内允许其他成员接同一公开话题，但必须保留发言者归属：A 说自己拥有某角色，不能变成 B 的持有条件。多个 Bot 的协议消息 ID 额外带连接命名空间，防止引用 ID 碰撞，不新增 Bot 白名单。

## 4. 再次呼唤时如何使用

1. 先执行原触发、插件开关、群白名单等检查。引用消息本身不绕过触发；@ 开关关闭时不会自动因引用而启动聊天。
2. 读取当前消息明确引用的原文，再选择近期聊天候选。原有 30 秒同用户历史补查保持用途，不升级为扫描一天群记录。
3. 参考优先级：当前用户明确意图 → 当前引用对象 → 当前活跃上下文 → 近期旧会话片段。优先级用于确定讨论对象，不能把旧回复当成已核实事实。
4. 有引用标识时，优先携带对应问答及少量前后片段；没有引用时，先按明确实体/当前发言者匹配，再提供少量最近问答。确定性筛选只选候选，不根据相似词强行断言是在续聊。
5. 同次聊天模型判断是续聊、换题还是需要澄清。不存在明确关联、多个话题都可能匹配时，简短确认，不硬套最近一段讨论。
6. 知识库、有效网页证据足够就答；只有旧对话而没有可靠事实依据时，旧对话仅帮助生成查询词，按已有搜索预算重新核实。

注入预算建议：近期片段合计最多 6,000 字符、最多 6 批；优先保留明确关联问题的起始问答，剩余空间给最新条件，避免只留“那这个呢”而丢掉对象。引用原文单独最多 4,000 字符、最多一层，总新增上下文不超过 10,000 字符。按消息 ID 去重，避免当前 session、旧片段、30 秒历史和引用原文重复出现；标记时间、发言者及截断，作为只读数据注入，不成为系统指令。

近期记录不合并进当前 sessionBatches，不重放历史回复、搜索动作或旧 followUp 倒计时。当前窗口结束仍正常销毁 session，仅保留独立的限期记录；再次触发创建新的 session。

## 5. 引用原文获取

- 优先从同范围的近期缓存匹配消息 ID。为支持引用派蒙的分段回复，发送链需要记录协议成功返回的消息 ID 与实际文字映射；适配器不提供 ID 时正常退化，不伪造映射。
- 缓存未命中时，仅针对用户本次明确引用的那一条消息做只读查询。不自动展开引用链、不遍历历史，不读取图片/语音/文件内容。
- 首版仅在核实过的 TRSS OneBotv11 + NapCat 上实现安全查询。现有框架 getReply/getMsg 经 sendApi，超时存在影响共享连接的风险，不能直接调用作为兜底；沿用独立 echo、独立超时与取消机制，具体单消息返回结构须在实现/验证时核对。
- 校验返回消息属于当前群或当前私聊、消息 ID 与请求一致、时间合理；无法证明范围时丢弃。允许引用同群另一位用户或 Bot，但归属保持原作者。
- 引用查询与原 30 秒历史补查共用最多 1,500ms 的补充上下文预算，引用优先；复用有界的初始化队列/并发限制，不逐项叠加长等待。读取失败仍处理当前问题，缺乏语境时询问，不伪装已看过原文。
- 本地近期缓存过期后，用户仍可以主动引用更早的消息。若协议允许且能验证范围，可以读取该条原文用于当前问题；这是本次明确提供的材料，不是恢复已过期的整段历史，也不自动认为旧攻略仍适用。

## 6. 统一时间配置，但不错误续期

启用配置如下（已有同名分组合并字段）：

```yaml
conversation:
  recentContext:
    enabled: true
    retentionMs: 86400000 # 1 天，搜索资料共用该时长
    persist: true         # 本地文件保存，跨 Yunzai 进程重启
    maxBatches: 20
    maxStoredChars: 16000
    maxPromptChars: 6000
    quotedMessage:
      enabled: true
      maxChars: 4000
```

默认模板 enabled=false，用户启用后按上述 24 小时工作。有效期限制为 5 分钟～24 小时，容量和并发另有硬上限。

近期衔接启用时，公开搜索缓存和会话证据统一使用 recentContext.retentionMs 作为最长有效期，已有 webSearch.cacheTtlMs 暂不参与选择；关闭近期衔接时恢复原 webSearch.cacheTtlMs。文档和元数据日志明确记录实际使用的时长，避免两个配置互相覆盖却看不出来。

“一致”指使用同一保留时长，不是强制所有内容同一时刻到期：

- 聊天按原始批次的交互时间过期，保存该批用户输入和实际发送文字；旧会话结束、再次读取、换 session 或导入上下文都不能刷新原时间。
- 网页按真实获取时间过期，命中缓存、复用资料或新增聊天不刷新 fetchedAt。只有成功重新获取才产生新的时效记录。
- 新对话只增加新的记录，不给整段旧历史续期。片段过期可能导致缺少话题锚点，此时需明确提问或引用原文，不能无限继承旧材料。
- 搜索空结果仍最多缓存 1 分钟，防止查不到的结果被保留一天；这是空结果防重复请求的特例，不是可用资料缓存。
- 活动截止、版本冲突、知识库修订/版本改变等可以提前让证据失效；24 小时不等于资料必然适用于当前时间。明确要求重新查证仍绕过缓存。
- 热改时长从原时间重算，缩短立即淘汰过期项；延长不会恢复已删除项，不能重新标记成刚获取。搜索 Key 隔离、单进程工具配额等原规则保持。

例如：今天 10:00 的问答和 10:01 获取的网页分别最长保留到明天 10:00、10:01。今天 11:30 再次问不会把旧资料顺延至明天 11:30；11:30 的新问答可独立保留到明天 11:30。凌晨重启后，只恢复原有效期尚未结束的记录；不会重新获得完整 24 小时。明天 12:30 明确引用今天 10:00 的消息时，可尝试单条读取旧原文、定位主题，再重新查证过期事实。

## 7. 生命周期、成本与验证

- memory.enabled 与近期衔接独立；不因为开个人记忆而自动开启衔接，也不因为关记忆而关闭衔接。
- 关闭近期衔接时清理近期聊天及关联索引（含持久化副本），并阻止在途引用结果迟到注入；删除群白名单资格、关闭插件同样清理相关聊天内容并复查发送许可。正常重启的 dispose 只取消任务/清内存，保留已成功落盘的未过期快照；要与用户明确关闭功能区分。启动恢复也须按当前开关和白名单过滤，不恢复已不允许的聊天。公共网页缓存按既有有效期和设置处理，不因清理群聊天而扩大可见范围。
- 当前明确要求“别接刚才的话题/换个话题”时提示模型遵从新意图，不继续推测旧主题；自动语义选题效果不能只靠离线测试保证。
- 不增加独立摘要/分类调用；补入文本会增加聊天输入 token。缓存命中可减少重复 Search/Fetch 请求，但新查询不同或资料失效时仍计费，不能保证总费用下降。引用查询不调用 DeepSeek 搜索接口。
- 日志只新增引用来源/耗时/片段数/有效 TTL 等元数据，模型请求正文继续遵循原 includePrompt。过期记录在读取时立即失效，并每分钟清理内存和持久化缓存，不自动删除原调试日志，不声称聊天文本从所有存储消失。

验收至少覆盖：关闭 memory 的同用户跨 session 续聊；同群其他用户引用接话且不混淆个人条件；私聊/群聊及多群隔离；多话题歧义；不相关新问题；原始时间过期与热改；晚到/错误范围的引用响应；不递归展开引用；旧片段不重复参与长期记忆、不恢复 followUp；网页命中不续期、过期后能由明确上下文重新搜索；窗口外普通消息不触发；缺少协议能力时正常降级；容量淘汰及重启恢复；原时间过期、损坏文件降级、写入中断不破坏上一份快照、关闭功能/移除白名单后的磁盘清理；persist=false 时重启清空。

真实联调需确认引用读取协议、发送 ID 映射、模型续聊判定、搜索专用 Key 与费用日志；不得只以模拟响应证明实际语义效果。本方案不包含服务器配置修改、推送、部署或重启授权。

## 8. 跨每日重启的文件保存建议

- 近期聊天和公开搜索证据分目录保存在插件 data 下，均排除 Git。文件不保存 API Key；搜索缓存凭证隔离沿用不可逆标识，不把搜索凭证写入正文或文件名。
- 每个正常文字片段发送成功、搜索成功或缓存清理后排队保存更新后的有界快照，不依赖重启前临时抢救。使用串行写入、临时文件加原子替换；突然终止最多可能丢失尚未落盘的最新部分，不能宣称零丢失。
- 启动先检查格式、容量、范围、原始时间和版本，再恢复未过期条目。损坏/不合法条目跳过并记元数据告警，不阻断机器人启动或回放旧消息。
- 保留同样的容量和输入预算；1 天是时间上限，并不保证繁忙群 24 小时内全部记录都存得下。
- 仅恢复历史资料，不恢复未完成发送、搜索请求、活跃窗口或补话计时器，防止重启后突然发送旧回复。
- Yunzai 软件重启不删除文件，适合当前每日重启场景。若要承诺容器重建后也保留，部署时还需核对 data 所在目录是否映射到宿主机持久卷；仅停止/重启同一容器与删除重建容器不同。
- 若用户以后主动设 persist=false，则恢复为内存模式；切换时应清理此前持久化副本，避免再次开启时复活旧数据。
