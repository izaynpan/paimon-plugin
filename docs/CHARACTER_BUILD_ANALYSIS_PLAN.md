# 角色养成分析：面板、喵喵评分与联网资料

日期：2026-10-31。状态：原神首版和铁道/绝区零扩展代码及离线验证已完成，分别见第9、10节；尚未部署或重启。第1～8节保留最初方案背景。

目标：用户问“我的芙宁娜还能怎么提升”时，读取该用户的真实角色面板，使用当前喵喵评分结果，检索适用的公开养成资料，返回一张原插件面板图和针对这套配置的建议。

## 1. 已核对的接入条件

- 方案核对基线为派蒙 `9529fcf`。当时 `paimon-runtime.js` 的面板 direct 分支会立即返回；`research.js` 将普通指令调用和搜索作为互斥动作。不能只靠增加提示词串起本需求。
- 服务器喵喵版本为 `929269ce`，本次仅只读源码，未读取用户面板或修改服务。
- `models/Player.js` 的 `getProfile(id)` 返回已有角色面板 Avatar，无面板时返回 false。
- `models/Avatar.js` 的 `getArtisMark(true)` 调用 `models/artis/ArtisMark.js:getMarkDetail`。输出包含总分、评级、逐件主副词条和分数、有效词条信息、每部位评分上限、实际使用的 `charWeight` 与 `classTitle`。
- `ArtisMarkCfg.getCfg(profile)` 的权重来自角色配置并结合当前武器/套装等条件计算；例如西风武器和绝缘套会触发相应修正。因此应调用实际评分器，不能仅读取一份通用权重表或由模型重新算分。
- `apps/profile/ProfileDetail.js` 通过 `profile.getArtisMark()` 生成面板上的评分，渲染入口支持 `e._profile`；没有该值时才走 `getProfileRefresh`。可据此设计同一快照的数据与图片输出，具体加载方式实施时复核。
- 当前已具备角色别名、群友目标解析、正常指令分发、知识库、Search/Fetch、查询预算及取消检查，可复用。

首版聚焦原神角色。星铁可复用流程，但评分字段、速度/击破和配队逻辑另行验证；绝区零不套用喵喵评分。提问者不额外输入指令前缀。清晰完整的分析请求可像已知角色面板请求一样独立唤醒，普通聊天、否定和引用继续遵守现有触发边界。

## 3. 执行流程

```text
当前用户消息
  → 识别“查看面板 / 养成分析 / 通用攻略”
  → 固定当前请求者、目标用户、游戏、角色及源消息
  → 读取本地面板，建立任务独立快照
      ├─ 原喵喵评分器 → 总分、逐件评分、实际权重
      ├─ 同一快照 → 原喵喵面板渲染 → 图片
      └─ 本地知识与公开攻略检索 → 适用机制、配装、配队条件
  → 校验数据单位、来源和缺失项
  → 模型结合三类证据形成分析
  → 原面板图一次 + 有优先级的建议
```

建议新增 `analyze_build` 任务类型，优先于普通面板 direct 分支识别。普通 `invoke_command` 与搜索互斥的规则保留；只有该分析任务允许组合面板读取、评分、渲染和公开检索，不让模型任意连调后台指令。

面板成功后，评分/渲染与公开资料检索可并行；模型最终分析等待必要证据就绪。推荐图片渲染完成即可先发，随后发分析，不额外发送“正在查询”的聊天铺垫。图片已发、分析失败时只补简短失败说明，不重复发送图片。

## 4. 面板和评分数据适配

新增一个有限职责的 `miao-profile-provider.js`：

- 通过原框架用户解析确定 UID/角色，只在内部使用账号标识。复用已加载的喵喵数据模型，不导入插件入口来触发初始化。
- 从当前本地面板读取角色等级、命座、天赋等级、武器等级/精炼、圣遗物套装/各部位等级/主副词条、最终静态属性、数据来源与更新时间。
- 调用当前评分器，获取真正用于面板图的评分结果与实际权重；必要时补充规则标题、适用条件和规则修订标识。
- 数值计算由程序完成，模型只解释。百分比、倍率、基础值与最终值分开存储，不拿显示字符串直接做算术；没有明确记录的战斗增益、层数和队伍条件标为未知。
- 输出稳定 DTO：`profileSnapshot`、`artifactEvaluation`、`dataQuality`。不给模型原始业务对象、完整账号文件或可执行评分源码。
- 每个任务使用独立模型实例/数据副本，因为评分器会修改 artis 的内存评分字段；冻结传给模型的 DTO，避免运行中更新导致图片与分析不一致。

渲染沿用原喵喵样式，向受控派生事件传入该任务的准备好面板，使用已核对的 `e._profile` 接点。该对象只能由适配层构造，不能来自模型参数；保留原请求者权限和正常回复通道，不修改共享处理器或向其他插件暴露全局钩子。

这一功能需要少量喵喵内部数据接口适配，区别于纯标准指令转交。接口变化时仅停用分析适配并回退普通面板，不重新给全部指令加 Git/哈希门禁。

## 5. 联网资料与证据合并

每次分析检查适用的公开养成证据：优先本地与有效缓存，缺少机制、配装或版本信息时使用现有 Search/Fetch。用户明确要求重新搜索时刷新；用户禁止联网、关闭搜索、耗尽额度或搜索失败时降级。

查询只包含公开游戏信息，例如角色名、武器名、配装/充能/配队主题；不包含 QQ、UID、群号、昵称、聊天原文或完整面板。模型最终分析接收必要的角色配置和数值，不接收凭证及无关个人资料。

证据分三层，不能互相冒充：

1. **面板快照**说明用户实际装备和现有属性，附更新时间。
2. **喵喵评分**说明当前评分规则下的词条价值和部位差距，不等同于实战最优或伤害提升百分比。
3. **公开资料**说明角色机制、适用队伍、循环和装备选择，附来源、适用版本及条件；与本地评分冲突时解释差异，不随意改分。

不要把“已拿到完整面板/评分”设成公开攻略知识的 `complete`，否则现有知识库优先检查会错误阻止必要搜索。知识库目前的角色背景或语音命中也不能证明培养策略已覆盖。

复用现有共享预算：建议整个分析任务最多3次模型请求（包括可能的意图识别）、2次Search、3次Fetch，公开搜索窗口默认15秒。明确表达可省掉额外识别请求；跨轮补查不能重置额度。模型超时与渲染超时分别控制；整个任务建议60秒上限，不重复执行来“碰运气”。

## 6. 分析内容与呈现

输出一张真实面板图，正文默认包括：

- 当前配置的关键事实和主要短板，引用实测面板数值，不套用空泛攻略。
- 最值得先做的2～3项改动，每项包含依据、具体操作及前提；优先等级、天赋、武器、明显不匹配主词条等确定性改进，再比较刷取成本与收益。
- 圣遗物按“规则下的差距 + 主副词条适配 + 实战需求”综合排序，不简单认定分数最低的一件一定先换，也不机械追求双暴。
- 配队未知时给条件化建议，最后只追问真正影响结论的一两个条件。不因缺配队就拒绝其余可完成分析。
- 少量实际使用的来源链接；明确说明分析基于哪次面板与当前评分规则。

首版不报虚构的“提升X%”。精确收益需要第二阶段接入喵喵伤害计算，并固定敌人、队伍、增益、手法和循环；用可复现的替换配置比较，不能把评分差值换算成伤害百分比。抽命座/专武不作为默认首选，用户有预算意图时才单独讨论。

## 7. 缺失、失败与生命周期

| 情况 | 行为 |
| --- | --- |
| 没绑定或没有对应角色面板 | 明确缺失项，提示 `#米游社更新面板` 或登录入口；不编造用户配置，不默认执行更新 |
| 面板较旧 | 标明快照时间，照常分析可用部分；可建议更新，不擅自刷新 |
| 评分接口不可用 | 能拿到面板则继续做有限分析，注明无法核对喵喵评分；不生成假分数 |
| 搜索失败/额度不足 | 仍返回图片和基于面板/规则的建议，说明哪些当前机制或版本结论未核实 |
| 图片渲染失败 | 有结构化数据时可以完成文字分析，说明本次图片未生成，不伪装已发 |
| 用户换角色/取消，或关闭功能、撤白、换Key | 取消该用户旧分析的后续检索/发送；已发图片不撤回、其他用户任务不串号 |

图片和文字共享任务ID、源消息、目标身份与快照摘要；同一任务不重复发图。首版不将面板/评分结果写进长期记忆或公共搜索缓存；公开网页按原缓存策略保存。日志默认记录耗时、来源ID、数据状态及失败原因，不记录整份私人面板。

## 9. 2026-10-31 首版实现

上述三个模块和运行时入口已实现，配置默认关闭，开启示例见 README。使用有限的明确个人分析语法，先于普通面板和聊天决策执行；不增加一次分类模型请求。普通公开培养问题继续走原聊天研究流程。

数据适配通过标准分发的内部 `profileHook` 完成：只在 `gs.panel.show` 的喵喵匹配处理器、原框架权限通过后建立独立运行事件，调用原 `getTargetUid` 解析绑定账号。只读当前 `data/PlayerData/gs/<uid>.json` 中该角色，使用 `new Avatar` 建立任务私有实例，再调用 `getArtisMark(true)`；不构造共享 Player、不触发自动刷新或保存。原 `ProfileDetail` 消费程序注入的 `_profile` 渲染同一份实例。用户事件和模型参数不能提供这个注入对象；该扩展不会改变普通指令分发。

模型 DTO 只白名单提取必要原始数值和公开名称，显式区分基础/静态最终属性及百分数单位；冻结 DTO 而不冻结原插件实例。角色原始/含命座天赋等级分别保留。评分失败返回 null，不自行重算。模型调用专用日志配置强制关闭请求和响应正文；仅记录随机任务ID、数据状态、评分是否可用、检索元数据、发送状态与耗时。会话结果为 `origin=command` 的无装备细节摘要，沿用记忆排除机制，不归档分析正文。

研究流程沿用 `completeWithResearch` 的三轮上限及现有共享服务，新增可选的程序查询生成器，同时替换模型提出的 Search 和本地补查查询。面板 DTO 不加入 `knowledge` 完整性元数据，避免阻止真正缺失的攻略查证。联网词限定为规范角色名和两个公开培养主题；不把聊天正文、昵称、UID、装备组合送给搜索服务。无联网权限仍可给有边界的面板分析，引用只使用本次有效来源映射。

图片与研究并行准备，仍只发一张图；图片失败会在分析文字中说明。当前首版总任务预算60秒；明确更新会占用同一预算，原更新处理器自己的回复保留。默认没有自动刷新。分析上下文只保存角色、目标和时间，两分钟内供同请求者消歧，不保存面板。相同消息五分钟内去重（最多2000项，进程内）；同用户新分析/面板或取消会撤销旧任务，他人闲聊不替换请求来源。旧任务失效后不会重新落入普通聊天执行。

开发时只读核对了服务器喵喵 `929269ce` 的接口。离线测试使用合成 Avatar 数据与真实 TRSS 分发快照，覆盖别名/目标、权限、快照隔离、数值单位、实际评分方法调用、隐私、预算、无数据和部分失败、刷新确认、取消、并发来源及日志。未读取真实账号作为测试样本，也未进行收费模型、生产图片或QQ实测；本地通过不代表线上建议质量已验证。未部署、未重启。

最终验证：新增专项测试21/21通过，完整 `node tests/run-tests.js` 436/436通过，`git diff --check` 通过。包括读取期间原处理器/权限撤销、重复投递不取消原请求、续话显式角色优先、撤销后同批新面板仍执行；没有收费 API 或私人账号样本。

## 10. 铁道与绝区零扩展（2026-10-31）

用户确认扩展三游戏。`buildAnalysis.games` 默认支持 `[gs, sr, zzz]`，总开关仍默认关闭；已有个人 `[gs]` 配置不会被覆盖。按原插件别名字典确认游戏和角色，跨游戏同名/别名先澄清；同用户分析续话保存游戏维度。各游戏使用各自的面板能力行与权限开关，默认读取已有快照；显式更新分别走 `#米游社更新面板`、`*米游社更新面板`、`%更新面板`，不改普通指令路由和已回退的抽卡功能。

- **铁道**：继续使用 `miao-plugin`。在通过框架权限的独立事件中调用原绑定解析，读取 `data/PlayerData/sr/<uid>.json`，用原 `Avatar` 和 `getArtisMark(true)` 评分；六个部位、光锥叠影、星魂、原始/含星魂行迹等级、速度、击破特攻、效果命中/抵抗等保留。开拓者只在已核对的同命途性别对中匹配，不借其他命途数据。原 `_profile` 渲染钩子消费同一份实例。
- **绝区零**：新增 `zzz-profile-provider.js`，对已加载的 `ZZZ-Plugin` 标准面板规则使用专用钩子。原 `getUID()` 解析账号；指定群友时先检查原插件 `query.others`，关闭后拒绝，不回落到本人。该方法临时改写事件 user_id 的行为在私有事件里恢复，权限仍使用原发送者。只读 `plugins/ZZZ-Plugin/data/panel/<uid>.json` 的指定角色，克隆后交给原 `formatPanelData`；其 `ZZZAvatarInfo` 构造器负责动态权重及逐件 `Equip.get_score`。保留音擎、影画、技能类型/等级、驱动盘套装/主副词条/单件总分和实际权重，不复制另一份评分公式。
