# 公告资讯与前瞻推送（2026-10-22）

本地实现，默认关闭，未部署、未进行真实 QQ 发送验证。代码全部位于 paimon-plugin，不修改框架或 genshin 受 Git 管理的文件。首次安装或更新 JS 后需要重启 Yunzai。

## 排查依据与目标

2026-10-22 只读核查服务器：原推送配置 `pushTime: 0 0/1 * * * ?`、`maxNum: 1`，日志确认每分钟执行。原模型每条发送前随机等待 10～90 秒，多个游戏依次处理。米游社静态列表响应实测命中 CDN 缓存，`X-Swift-CacheTime: 600`；加时间参数的请求当时返回 MISS。这不能证明所有五分钟延迟都来自缓存，也不能保证未来上游不改变缓存策略。

10 月 21 日 12:00:14 的原神前瞻特别节目预告（帖子 79040314）归于活动栏目 `type=2`，原自动推送只抓 `type=1/3`。该帖当前已超过默认两小时窗口，安装后不会自动补发。

目标：在派蒙插件中增加独立推送模块，公告、资讯照常，活动栏目仅定向补充前瞻；同群三个游戏共用发送间隔，不再依赖原随机长等待。无需模型、Key、长期记忆、聊天会话或搜索功能。

## 启用与回退

1. 更新 paimon-plugin 代码。
2. 在 `plugins/genshin/config/mys.pushNews.yaml` 中将 `maxNum` 改为 `0`，保留 `gs/sr/zzz` 的 `announceGroup/infoGroup` 和 `banWord`。这是 genshin 已忽略的用户配置文件，不要改 `defSet`。该设置关闭原模型所有游戏的自动公告资讯发送；如还订阅崩坏三等其他游戏，它们也会停止，当前新模块只承接原神、星铁、绝区零。原活动到期预警不受该字段影响。
3. 在派蒙个人 `config/config.yaml` 合并：

```yaml
newsPush:
  enabled: true
  games: [gs, sr, zzz]
  pollIntervalMs: 30000
  sendIntervalMs: 30000
  includePreviews: true
  maxAgeHours: 2
  requestTimeoutMs: 10000
```

4. 重启 Yunzai 完成切换，避免原模型已经读取旧配置、正在随机等待的批次与新推送重叠。新模块启动时若原 `maxNum` 不是 0，将拒绝接管并提示重启；运行中发现原推送重新开启也锁定接管，不能简单来回改开关绕过这次切换。

新模块不会自行修改原配置，不会部署或重启。原 `#开启/关闭公告推送`、`#开启/关闭资讯推送` 继续维护订阅，新模块每轮及每次发送前直接读取用户配置，因此可沿用；手动查询原公告、资讯、活动不变。原主人的手动推送指令仍受 `maxNum=0` 影响，不能用它补发。

后续 `newsPush` 参数可热更新，关闭后丢弃未发队列并取消在途公开请求。关闭期间不积累新队列；重新开启会重新扫描窗口内帖子。`games: []` 不接管任何游戏。顶层聊天 `enabled`、聊天 `groupWhitelist`、聊天 Key 均不约束新闻；新闻的发送范围仅取原订阅群，请通过原订阅配置或 `newsPush.enabled` 管理。

回退时先关闭 `newsPush.enabled`，再恢复原 `maxNum`，建议重启以清理在途任务。恢复后原随机延迟、栏目范围、缓存行为仍然存在；新发送记录未回写旧 Redis，原功能可能重发最近两小时内新模块已发的帖子，需在切换时避开这个窗口。不要删除发送日志来“刷新”，否则会丢失去重信息。

## 运行规则

- 框架每 5 秒调用一次轻量调度；关闭时不抓取米游社。实际列表扫描默认每 30 秒，单次任务不会重入；每个已订阅的游戏/栏目读取前 20 条，最多同时 3 个请求，单栏目失败不阻断其他栏目。HTTP/JSON/业务返回/列表形状校验，单请求默认 10 秒，可调 1～30 秒，响应限 4 MiB。
- 列表请求添加 30 秒时间桶参数和 no-cache 请求头，减少一直命中旧 CDN 条目的情况；不承诺上游即时发布或永不缓存。检查周期范围 30 秒～10 分钟，不调用 DeepSeek、不传 QQ 消息或密钥。
- 公告 `type=1` 发到公告订阅群；资讯 `type=3` 发到资讯订阅群；活动 `type=2` 仅保留标题含“前瞻…特别节目 / 前瞻…直播 / 特别节目…预告”的帖子，发到资讯订阅群。标题规则不保证覆盖未来所有官方命名方式，不是 AI 分类。
- 保留原 `banWord` 正则过滤，包括活动补入的帖子。例如原星铁屏蔽词有“直播预告”，命中的前瞻直播标题仍会被屏蔽；要接收时需在用户配置中移除对应词。无效正则报源错误，本轮不绕过过滤发送。
- 默认只接纳发布两小时内且不是未来时间的帖子，范围可调 0.5～24 小时。只查前 20 条，不做全站分页补历史；突发大量发帖或长时间故障仍可能遗漏。首次启用可能补发窗口内未发帖子，不追补更老内容。
- 同群按发布时间排队，三个游戏、公告资讯共用一个节奏，默认两次发送至少间隔 30 秒（可调 30 秒～10 分钟）。每次调度每群最多尝试一条，渲染、网络、5 秒调度粒度和前序群处理可能使间隔更长，不承诺每条恰好 30 秒。队列最多 2000 个群/帖子项。
- 同群多 Bot 订阅合并，只选当前可用的一个发送；优先配置遍历中第一个可用 Bot，在线群表可用时检查成员关系。不会为每个 Bot 重复推同一帖子。无可用 Bot 暂留队列，在窗口内继续尝试。
- 兼容读取原 Redis `Yz:<game>:mys:newPush:<bot>:<group>:<post>`，任一个订阅 Bot 已有标记就跳过。这沿用旧标记语义：原模型在发送前就标记，无法仅凭它证明历史发送成功。Redis 读取失败时停止本轮，避免迁移时重复。
- 复用 genshin `MysNews.newsDetail/render/replyMsg` 和原图片模板，仅实例级替换网络读取为有超时的公开请求。不替换原类方法、不取消原定时任务、不改第三方源码；上游方法签名或模板变化仍可能需要适配。模块导入及渲染失败会记录并有限重试，不能把没有 Git 冲突说成永久兼容。

## 发送记录与故障边界

`data/news-push/delivery.json` 为本插件独立、被忽略的原子替换日志，只保存群/游戏/帖子 ID、状态、次数和时间，不保存聊天正文或文章正文。已发送/待核查记录和群节奏保存 48 小时，进程重启后继续去重。该文件只允许一个 Yunzai 进程使用，不支持多进程或共享目录竞争。

- 图片生成失败或协议明确拒绝：至少一分钟后重试，包含首次最多三次，次数跨重启保存；过期停止，失败项不会持续堵住同群其他文章。
- 提交协议前先保存 `uncertain` 预约，成功回执才改为 `sent`。网络抛错、空消息 ID、部分图片成功、未知返回结构都保留 `uncertain`，日志提示人工核查，不自动重发。这样可能漏发崩溃发生在预约之后、真正提交之前的帖子，但不会因无条件重试重复轰炸。
- `news_uncertain` 记录需要根据实际群消息核查，未实现聊天补发指令。可以用原 `#活动` 等查询最新帖子；这属于用户主动查询，不会更改自动发送记录。
- 文件损坏、无权限、超过 8 MiB 或写失败时本轮不提交新消息，保留已有文件。不要通过自动清空文件继续运行。
- 关闭开关、撤订阅、修改屏蔽词或游戏范围、卸载，在后续检查时阻止尚未提交的发送；已发出的协议请求无法撤回。原用户配置没有跨进程事务，极窄的读配置至提交之间仍非原子撤销。
- 独立配置监听不占用聊天的重载回调。新 TRSS 提供 `addCleanup` 时释放该监听并取消本模块请求；旧框架的首次安装/更新使用进程重启，不承诺仅替换 JS 即可完整热卸载。
