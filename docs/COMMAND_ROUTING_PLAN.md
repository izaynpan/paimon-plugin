# 指令纠错与自然语言调用方案

方案日期：2026-10-18；实现更新：2026-10-19。状态：**已按主人结果列实现本地首版，默认关闭，未部署。** 批准范围见 [服务器功能清单](SERVER_COMMAND_CATALOG_2026-10-18.md)，原始定位见 [源码索引](SERVER_COMMAND_RULES_2026-10-18.md)。下方保留设计说明；实际首版差异与验收见第 10 节，结果列优先于旧的“建议先接少量”描述。

## 1. 要达到的体验

第一步只提醒：

| 用户输入 | 预期行为 |
| --- | --- |
| `#芙宁娜攻路` | 在攻略功能被选中、原插件未回复且候选明确时，提示“想看攻略的话，用 `#芙宁娜攻略` 就好啦” |
| `#体立` | 体力被选为 n，不提醒、不代执行 |
| `%艾莲面版` | 如果原插件未处理，推荐 `%艾莲面板` |
| `#芙宁娜面版` | 喵喵已经支持“面版”，原插件正常处理，不纠正 |
| `#绑定` | 若选中格式帮助，可提示缺少 UID；不捏造 UID、不执行绑定 |
| `#体力` 但尚未绑定 / CK 过期 | 交给原插件提示前置条件，不说指令拼错 |
| `#重起` | 默认不推荐或代执行重启；管理功能仅按主人筛选和权限另议 |
| 引用别人发的 `#体力`、粘贴代码含 `#` | 不当作本人的新执行请求 |

第二步可以代查：

| 用户输入 | 预期行为 |
| --- | --- |
| “派蒙，看看我原神原石收入” | 调用已批准的本人原神账本能力，由原插件发送结果 |
| “派蒙，给我看看芙宁娜面板” | 解析为角色面板，而不是公开图鉴 |
| “派蒙，发一张芙宁娜攻略” | 调用攻略图；返回原插件图片 |
| “派蒙，看看绝区零这期式舆” | 调用 `%式舆` 对应能力 |
| “派蒙，帮我看看面板”且无游戏语境 | 澄清游戏和角色，不默认原神 |
| “面板是什么”“如果查面板会怎样”“不要查面板” | 解释 / 闲聊 / 否定，不执行 |

上述都是验收目标，不是当前模型已经具备或验证过的准确率。

## 2. 已核实的框架限制

依据服务器快照：

- `lib/plugins/loader.js:227` 的 `deal(e)` 先执行黑白名单、冷却、事件解析、回复包装、Runtime、插件启用过滤与上下文，再处理前缀、`accept` 和规则。
- `:291` 会先跑插件 `accept`。喵喵 `components/App.js` 和 `apps/wiki/CharWiki.js` 可把 `#角色技能` 改写为内部 `#喵喵WIKI`，并补 `e.char/e.wikiMode`。
- `:298` 按优先级处理规则。**返回 false 才继续**；undefined 也算消费。异常和权限失败后同样会退出这一轮，派蒙收不到后续机会。
- `deal(e)` 没有“哪条命令成功、哪条未处理”的结构化返回值；发了消息也不一定 return true。
- Atlas 当前 `priority=10, success=false`，可能发送图片之后 return false。词条、小瑶等也有宽匹配，不能仅凭正则命中作结论。
- 派蒙 `apps/chat.js` 为 priority 99999 的兜底；`lib/trigger.js` 默认忽略 `#/＃/*/%`。只改提示词不会让这类消息进入纠错流程。
- `auto-plugin/app/autoCommand.js` 已有构造事件再 `PluginsLoader.deal(e)` 的做法，但不能直接当通用工具：会重新经过冷却、重复消息过滤、上下文及所有监听器，也缺少本方案的能力限制和执行结果协议。

**第一版可以只修改派蒙插件，但不能声称覆盖所有“指令没有执行”的情况。** 已被前置上下文、其他插件、权限检查或冷却消费的消息，纯兜底无法精确诊断。

## 3. 先建人工批准的能力目录

区分三个目录：

1. **发现目录**：扫描到的正则、帮助与动态资源，方便更新清单。发现不代表授权。
2. **批准目录**：主人从清单中选择的功能，每个分别设置 `suggest` 和 `invoke`。
3. **当前可用目录**：批准项与已加载插件、事件类型、当前群启用状态、用户权限、适配器兼容版本的交集。未知权限或准备流程的能力只做提示。

建议一个能力描述包含：

```json
{
  "id": "genshin.profile.show",
  "title": "查看本人原神角色面板",
  "suggest": true,
  "invoke": false,
  "game": "gs",
  "arguments": { "character": "known-character-name" },
  "targetPolicy": "self",
  "effect": "query_with_cache",
  "requires": ["bound_uid", "profile_data"],
  "adapter": "miao-profile-detail",
  "example": "#芙宁娜面板"
}
```

这是目录格式示意，并非现在可直接填写使用的配置。`invoke` 要在主人筛选和对应适配验证后才能开。游戏、角色、时期、序号、UID 是结构化参数；发到模型的目录只包含当前可选能力。凭证查询、任意 Shell/JS、更新重启不提供为模型工具。

角色别名优先复用插件已有角色库；没有已确认的解析接口时，使用只读提取的名称/别名快照并记录来源版本。不能导入整个插件来“提取正则”，否则会启动定时任务或触发初始化写入。动态资源增删后更新目录，热卸载后立即停用能力。

权限既看 `rule.permission`，也看函数内部检查。例如喵喵重置排名提示语说管理员，实际代码检查 `e.isMaster`；不能靠帮助文字判权限。

## 4. 阶段一：错误格式与错字提醒

### 接入位置

建议在 paimon-plugin 内增加轻量观察入口和独立纠错入口，原聊天过滤保持原用途。

- 观察入口在可控的早期 `accept` 位置记录原消息标识、原始文本，包一层本事件的 `e.reply`，只记录回复尝试/结果，不存正文；始终不消费消息，不修改权限，不启动模型请求。
- 纠错入口安排在普通业务插件之后、派蒙聊天之前。它只看当前直接输入的命令文本，不读取历史、引用或长期记忆来触发纠错。
- 已观察到任何回复尝试时，保守跳过纠错，处理 Atlas“已发图仍放行”的情况。外部插件直接用 Bot 发送、绕开 `e.reply`，或者更早的 `accept` 已消费，观察器不能完整覆盖；对这类冲突不启用自动纠错，不能靠等待几秒推断成功。
- 初始建议与派蒙共用插件总开关、群白名单、私聊开关；命令建议是否要求点名可单独配置。建议群内以明确命令前缀为触发信号，不要求额外叫派蒙，但仍尊重框架 onlyReplyAt。

### 决策流程

1. 在框架既有转换的基础上处理首尾空白、明确的全角符号，保留游戏含义；`%` 不能纠成 `#`。
2. 按当前用户、群和已批准功能形成候选集合，识别是完整指令、缺参数、未知角色还是疑似错字。
3. 若有效命令在原插件条件下可能因数据问题失败，不再建议改写该指令。宽规则命中不能阻止合理纠错，也不能证明执行成功。
4. 优先本地别名、有限编辑距离、词序与参数校验；要支持同音误字时可增加小型拼音索引。建议先容忍一个明显错字，短命令更严格，阈值通过合成样本确定。
5. 候选唯一且差距足够时给一条正确示例；两个候选接近时给最多两项；没有把握就不打扰。不能为了覆盖率把陌生词都改成游戏角色。
6. 可选语义兜底只在本地筛出少量候选时用模型选 ID，不允许生成目录外指令。首版建议先不依赖模型做错字纠正，降低延时和费用。
7. 只提醒一次，不自动执行“猜出来的正确命令”。用户再发送正确指令时走原插件。

建议每用户每群 30 秒最多一条纠错提示，同一原消息只处理一次；数字为初始设计值，可热更新并以实际误报情况调整。UID、兑换码等参数不能用编辑距离自动修正。

## 5. 阶段二：自然语言调用

### 意图判定与当前聊天整合

群聊默认仅在点名 / @派蒙后允许发起调用；自然聊天的 90 秒活跃窗口不自动赋予所有群消息执行资格。可以另选“同一用户的明确续问”模式，但不得继承其他群友的执行意图。私聊遵守原开关。

在现有聊天决策中增加互斥的 `answer / clarify / invoke_command` 分支。只有需要调用时传入少量检索出的能力与参数约束；模型返回能力 ID 和结构化参数，程序再验证。无需为了每次闲聊额外跑一遍全量指令分类器，也不把 416 条原始声明塞进提示词。

示意：

```json
{
  "action": "invoke_command",
  "capabilityId": "genshin.profile.show",
  "args": { "character": "芙宁娜" },
  "sourceMessageKey": "程序提供的当前消息引用"
}
```

`sourceMessageKey` 只能从程序提供的当次消息集合中选择，并须与能力请求的原作者绑定；不接受模型给出的 QQ、群号、Bot 账号或权限字段。模型自报“高置信度”不能代替参数、来源和权限校验。

派蒙当前会合并不同用户消息，批次回复使用最后一条事件。**调用绝不能直接使用批次最后一条事件作为申请人。** 首版建议一个批次最多处理一个明确请求；多个用户分别请求或归属不明时拆回各自事件排队 / 澄清。会话记忆、触发前历史、引用消息、网页、知识资料、无人接话补话，都不能独立产生执行授权。

执行和普通聊天共用 session 串行调度；命令分支不再同时发一段普通聊天答复、不启动 followUp，不循环调用模型。原插件已经给出图片、文字或缺绑定提示时，直接结束本轮。必要的成功摘要可写入短期上下文，但不把任意插件输出变成长期用户记忆，不把“已请求”写成“已成功”。

### 推荐执行方式：逐能力适配桥

**第一版优先在派蒙中实现少量、经过验证的目标插件适配器。** 不把模型生成的文本发到群里让 Bot 再读，也不无条件调用全局 `Bot.em()` / `loader.deal()`。

每个适配器负责：

1. 获取当前加载器中预期插件与处理器，核对兼容签名 / 版本，拒绝已卸载或未审查的变更。
2. 从原用户真实事件派生独立事件，保留 `self_id/user_id/group_id`、发送通道、群成员、引用及明确允许的目标信息；不伪造主人或管理员，不借用默认 Bot。
3. 用程序模板生成规范命令，统一设置 `msg/raw_message/original_msg/message` 与 `game/isSr/isGs`。不要沿用已被别的插件重写的内部消息。
4. 建立与派生事件绑定的 Runtime / 用户对象；不能简单浅拷贝原 `runtime/user`，它们可能仍引用旧事件。具体构造依各插件源码验证，不在未验证前宣称支持任意处理器。
5. 复查黑白名单、插件启用、事件类型、目标规则权限及能力自身权限；原函数内部权限仍正常执行。能力适配器只能比原功能更严格，不能提升权限。
6. 执行该能力必要的准备过程。例如喵喵资料必须跑已审查的 `CharWiki` 准备路径或隔离事件上的对应 `accept`，再校验目标规则和 `e.char/e.wikiMode`。不能直接调用 `#喵喵WIKI`，也不能重新运行全体插件的任意 `accept`。
7. 调用目标插件公开注册处理器，使用原作者事件对应的 `e.reply` 发送文字、图片或转发结果；不把图片交给模型重新转述，也不修改原图片。需要直接 `Bot.send*` 的功能首版不接，除非单独适配所有发送出口。
8. 记录 `attempted / responded / no_response / rejected / failed` 等执行状态。处理器返回 undefined/true 只能表示返回情况，不能作为业务成功证明；已回复“请先绑定”算 responded，不算查询成功。

直接适配会绕过全局重新入站，因此必须显式保留原准入判断与插件内部冷却；不能声称天然继承了整个 `deal()` 的行为。原事件已通过的入站冷却不重复扣同一次配额，但真正发起时检查最新黑白名单、开关、权限及能力独立冷却。

### 防重复、取消与结果一致性

- 使用 Bot + 会话范围 + 原用户 + 原 message ID + 能力 ID 的执行键；同一消息只允许调用一次，无消息 ID 时生成接收期唯一键。
- 合成事件加不可由用户文本控制的内部标记，派蒙路由和观察入口跳过合成调用，最大调用深度为 1。
- 首版每个明确请求最多一项能力；不允许“列出全部能力然后逐个执行”、串接命令、多步任意规划或通过定时指令转发。
- 参数仅允许已定义类型、字符长度、枚举、数值范围；角色必须解析到已知实体。目录项仅接受本人目标，除非主人明确开放“查某人”且原插件允许。
- 给每次调用设置等待期限与独立冷却，插件内真实请求不能保证可中止。超时后禁止自动重试，保留去重状态；避免第一次迟到与第二次结果重复。
- 在执行前和每次派生 `e.reply` 前检查开关、群白名单、dispose、取消代次；关闭后阻止未发送的回复。已发网络请求、已写缓存或已提交协议消息不能撤销。
- 原插件输出完整保留。默认不加“执行成功”的固定尾句；无法判断结果时记录不确定，不能由模型补写一个查询数字。
- 插件原回复不强制套派蒙长文本分段节奏，避免图片查询被拖延；同聊天发送顺序与派蒙发送时钟的整合需在桥接接口测试中明确。

## 6. 若以后需要更广泛兼容

可以另行讨论框架增加一个很小的稳定分发接口：返回 `unmatched / handled / denied / throttled / failed`，提供只经过已批准目标的分发方式和回复观察，不重复执行入站统计、上下文或自动监听器。该接口比 monkey patch 全局方法更容易维护，但要修改框架，**不属于本次已决定实施的范围**。

纯插件版保留以下边界：被提前消费的错指令无法兜底；返回 false 且绕过 e.reply 的插件无法准确判定是否发过；某些内部准备和多步上下文功能只能展示正确用法。用户筛选后若这些功能不重要，就没有必要扩到框架层。

## 7. 与派蒙现有能力的边界

- 默认总开关关闭，`suggest` 与 `invoke` 分开开启；目录内容不随模型输出变化。新增 JS 需要重启，纯目录配置后续可设计热更新。
- 现有 `ignoreCommandPrefixes` 继续保护普通聊天；纠错走独立路径，不能删除过滤后把所有运维指令送给聊天模型。
- 提示结构遵守 [提示词整理约定](PROMPT_REFACTOR.md)：persona 保持身份与表达，能力协议放在程序构建层，模型只在开放时看到能力清单。
- 原神查询属于现有人设范围。星铁、绝区零和点歌等若选中，可作为独立工具意图路由，先于普通闲聊的“世界外话题”策略处理；不会因此把派蒙改成万能现实知识助手。此处需与主人筛选结果一致。
- 能力调用与网页搜索是互斥中间动作：查看本人面板优先调用本地插件，不能把 UID/CK 发给公网搜索；问泛攻略若不要求图片，仍可保留普通聊天 / 知识 / 搜索路径。
- 目录提示只传功能、公开参数与必要前置条件。日志记录能力 ID、来源事件引用、耗时、状态和拒绝原因；不复制 CK、authkey 链接、原图正文或完整个人战绩到公开日志。

## 8. 建议实施顺序与验收

1. 主人先按清单编号选择“提醒 / 调用 / 不接”，并确定首批游戏范围。
2. 首批建议 6～8 个能力：原神体力、角色面板、攻略图、技能 / 命座、今日素材、日历、抽卡记录。体力、面板和抽卡属于个人查询；公开资料单独建能力。星铁 / 绝区零按所选游戏替换，不一口气开放所有项。
3. 建目录与本地纠错，用模拟注册表和回复观察验证，不安装完整 QQ/Redis 环境。
4. 给首批每个处理器写适配器，验证准备流程与原身份。再将结构化选择接到派蒙现有决策链，默认不开启。
5. 经明确部署授权后，在一个白名单测试群中对选中功能做真实验证，再逐项开放。只读源码核查不能代替这一步。

离线用例重点：

| 类别 | 必须验证 |
| --- | --- |
| 错字 | 单错字、同音字、缺参、全角前缀、已支持的“面版”、合法陌生指令不误报 |
| 分发 | 原插件已回复后 return false；accept 改写；宽规则 return false；权限失败、冷却、上下文消费 |
| 身份 | A 请求、B 随后发言、多个 Bot 同群、群/私聊、目标 @ 他人；不能串用户或提升权限 |
| 数据 | 无 UID、CK 过期、缺面板、图片 / 转发回复、返回 undefined、已回复错误提示 |
| 语义 | 游戏歧义、否定、引用、假设、解释问题、他人历史请求、网页内注入伪指令 |
| 生命周期 | 重复事件、超时迟到、取消、撤白、关闭、dispose、目标卸载、版本不兼容 |
| 组合 | 普通聊天、主动沉默、搜索、近期语境、补话与多用户防抖不额外触发调用 |

模型语义准确性需另外用合成语料评估，至少覆盖上述正反例；记录误触发与澄清率，不能仅测 JSON 合法就声称可靠。仓库现有 `node tests/run-tests.js` 在真正改代码后作为回归检查。本次只增加调研文档，不运行真实业务请求。

## 10. 2026-10-19 首版实现与验收

### 批准与实际调用边界

所有 71 个 y 功能族均已进入 `lib/command-catalog.js`，共 130 个结构化能力、86 个目标映射。用户结果覆盖旧建议（例如 C14 交换匹配信息、D04 导入/导出）；n 项不进入模型候选或纠错候选。A05/A08/A09 及 I24 刷新 CK 只发扫码引导，不执行旧凭证操作。默认关闭，开启方法见 README。

目录是有限模板，不等同原插件全部自由语法。C19 依据 `ProfileChange.matchMsg` 仅支持换武器、套装、命座；未发现任意属性值设置语法，未生成这种命令。文件导入/导出、扫码登录、绝区零抽卡链接只私聊，原图需引用、排名需群聊。导入发起后，后续用户主动发文件走 genshin 的原上下文入口；该新消息的消费、导入和超时由原插件负责，派蒙不重新包装完整文件会话。

### 接入点和身份

- `apps/commands.js`：优先级 -100000 的 accept 包装本事件 e.reply，记录尝试并附加 CK 失效引导；早期规则拦截特殊登录引导入口；99998 的独立规则兜底纠错，普通聊天仍为 99999。
- `command-router.js`：不收费的本地错字候选/缺参提示、权限/可用性过滤、最多 24 个相关能力检索，提供当前源消息引用；不同用户同时点名时先澄清。同一用户一批以最后一条明确请求为源，历史与引用没有独立执行资格。
- `ConversationBuffer` 只在调用回调时提供临时 event 数组；历史补入消息没有 event，event 不进入持久化/提示。模型不能给 QQ、UID、Bot 或权限。校验实体来自当前源文本的已知名称/别名；游戏须明确或能从唯一游戏实体/术语确认，不能靠模型猜游戏或从历史补造角色。
- `command-bridge.js`：只找已加载的指定 owner/name/method；重新建立 Runtime，避免旧 runtime/user 指向最后发言者。仅喵喵 wiki 跑目标 accept；小瑶只调用两个审查过的 export，不跑全量 dispatch。未重入 loader.deal/Bot.em，不重复入站统计和冷却。
- `command-manifest.json`：钉住 10-18 的框架/插件 Git 版本、入口文件与关键准备/适配文件 SHA256。不是全依赖完整性证明；改变下游实现也需要重新审查。更新后不兼容即退出候选；只读诊断脚本见 README，不提供配置绕过。
- 实体只读来自已加载喵喵 Meta、Atlas 公共索引/原魔别名、ZZZ 公共角色映射/别名；未发现或无法确认的实体拒绝。没有导入整个插件扫描、联网补名单或读取个人配置密钥。字典缓存 60 秒，资源实际覆盖仍取决于现场。

### 决策、取消与结果

调用在原聊天请求的首轮选择，与 search/lookup_local 互斥；搜索后轮次不再提供能力协议，即使返回 invoke_command 也不执行。最终回复格式和中间调用格式分离，persona 未扩写。群内普通活跃续话、补话、记忆、网页和引用不会获得执行资格；一般攻略讨论保留普通聊天/知识/搜索路径。

请求在同 session 队列中执行，最多一项能力。原插件已有任何回复尝试则不重试、不追加另一能力。responded 只表示发送过回复，可能是“缺绑定”等错误提示，不表示业务成功。图片、转发和文件保持原发送通道，输出不送回模型；不发额外表情、不启动 followUp，命令批次标记 origin=command 并排除长期记忆。真实输出以 0 字更新派蒙发送时钟；插件自身回复不增加打字等待。

每次执行前及派生发送前复查开关/群白名单、身份、插件加载/兼容、原权限。热重载发生相关准入变更会废弃旧选择；同请求者明确取消会阻止其待调用/迟到发送。一般等待 30 秒、扫码登录 180 秒；源消息内存去重 1 小时（最多 10000），提示和调用分别 30 秒冷却。超时不重试；第三方执行中的请求/缓存/认证写入不能回滚。

纯插件观察仍有覆盖限制：框架前置冷却/上下文或更早插件已经消费时无法兜底；直接 Bot.send 等出口无法由 e.reply 观察器完全确认。字符纠错只处理小编辑距离和有把握的候选，最多两项；不猜 UID、凭证或多错字陌生实体。语义意图仍依赖模型，不声称完全避免误判。
