# 指令纠错与自然语言调用方案

方案日期：2026-10-18；实现更新：2026-10-24。状态：**已改为标准指令转交，本次代码尚未部署；服务器此前已开启旧版配置。** 批准范围见 [服务器功能清单](SERVER_COMMAND_CATALOG_2026-10-18.md)，原始定位见 [源码索引](SERVER_COMMAND_RULES_2026-10-18.md)。下方保留设计说明；当前实现与验收见第 10 节，结果列优先于旧的“建议先接少量”描述。

## 1. 要达到的体验

第一步只提醒：

| 用户输入 | 预期行为 |
| --- | --- |
| `#芙宁娜攻路` | 在攻略功能被选中、原插件未回复且候选明确时，提示“想看攻略的话，用 `#芙宁娜攻略` 就好啦” |
| `#体立` | 体力被选为 n，不提醒、不代执行 |
| `%艾莲面版` | 如果原插件未处理，推荐 `%艾莲面板` |
| `#芙宁娜面版` | 喵喵已经支持“面版”，原插件正常处理，不纠正 |
| `#绑定` | 若选中格式帮助，可提示缺少 UID；不捏造 UID、不执行绑定 |
| `#体力` 但尚未绑定 / CK 过期 | 交给原插件提示前置条件，不说指令拼错 |
| `#重起` | 默认不推荐或代执行重启；管理功能仅按主人筛选和权限另议 |
| 引用别人发的 `#体力`、粘贴代码含 `#` | 不当作本人的新执行请求 |

第二步可以代查：

| 用户输入 | 预期行为 |
| --- | --- |
| “派蒙，看看我原神原石收入” | 调用已批准的本人原神账本能力，由原插件发送结果 |
| “派蒙，给我看看芙宁娜面板” | 解析为角色面板，而不是公开图鉴 |
| “派蒙，发一张芙宁娜攻略” | 调用攻略图；返回原插件图片 |
| “派蒙，看看绝区零这期式舆” | 调用 `%式舆` 对应能力 |

上述都是验收目标，不是当前模型已经具备或验证过的准确率。

## 2. 已核实的框架限制

依据服务器快照：

- `lib/plugins/loader.js:227` 的 `deal(e)` 先执行黑白名单、冷却、事件解析、回复包装、Runtime、插件启用过滤与上下文，再处理前缀、`accept` 和规则。
- `:291` 会先跑插件 `accept`。喵喵 `components/App.js` 和 `apps/wiki/CharWiki.js` 可把 `#角色技能` 改写为内部 `#喵喵WIKI`，并补 `e.char/e.wikiMode`。
- `:298` 按优先级处理规则。**返回 false 才继续**；undefined 也算消费。异常和权限失败后同样会退出这一轮，派蒙收不到后续机会。
- `deal(e)` 没有“哪条命令成功、哪条未处理”的结构化返回值；发了消息也不一定 return true。
- Atlas 当前 `priority=10, success=false`，可能发送图片之后 return false。词条、小瑶等也有宽匹配，不能仅凭正则命中作结论。
- 派蒙 `apps/chat.js` 为 priority 99999 的兜底；`lib/trigger.js` 默认忽略 `#/＃/*/%`。只改提示词不会让这类消息进入纠错流程。
- `auto-plugin/app/autoCommand.js` 已有构造事件再 `PluginsLoader.deal(e)` 的做法，但不能直接当通用工具：会重新经过冷却、重复消息过滤、上下文及所有监听器，也缺少本方案的能力限制和执行结果协议。

**第一版可以只修改派蒙插件，但不能声称覆盖所有“指令没有执行”的情况。** 已被前置上下文、其他插件、权限检查或冷却消费的消息，纯兜底无法精确诊断。

## 3. 先建人工批准的能力目录

区分三个目录：

1. **发现目录**：扫描到的正则、帮助与动态资源，方便更新清单。发现不代表授权。
2. **批准目录**：主人从清单中选择的功能，每个分别设置 `suggest` 和 `invoke`。
3. **当前候选目录**：批准项与派蒙开关、会话/来源条件和参数约束的交集。纠错仅提供目录里的标准名称；自然语言转交还要求框架入口可用。是否有处理器、权限与业务前置条件由实际分发决定，候选不保证业务可用。

建议一个能力描述包含：

```json
{
  "id": "genshin.profile.show",
  "title": "查看本人原神角色面板",
  "suggest": true,
  "invoke": false,
  "game": "gs",
  "arguments": { "character": "known-character-name" },
  "targetPolicy": "self",
  "effect": "query_with_cache",
  "requires": ["bound_uid", "profile_data"],
  "template": "{character}面板",
  "example": "#芙宁娜面板"
}
```

这是目录格式示意，并非现在可直接填写使用的配置。`invoke` 要在主人筛选和标准指令模板验证后才能开。游戏、角色、时期、序号、UID 是结构化参数；发到模型的目录只包含当前可选能力。凭证查询、任意 Shell/JS、更新重启不提供为模型工具。

角色别名复用插件已有角色库：读取已加载喵喵的共享 Meta 数据/别名；绝区零只读角色 JSON 与默认/自定义 alias.yaml，遵守自定义键覆盖默认数组、顺序匹配规则，完整名统一为角色短名。Atlas 仅补充名称，不覆盖源插件规范名称；七圣卡牌分类跳过。不能导入整个插件来“提取正则”，否则会启动定时任务或触发初始化写入。词典缓存60秒，动态资源增删后按需重读；处理器卸载后不会继续执行旧实例，未处理时提示手动指令。

权限既看 `rule.permission`，也看函数内部检查。例如喵喵重置排名提示语说管理员，实际代码检查 `e.isMaster`；不能靠帮助文字判权限。

## 4. 阶段一：错误格式与错字提醒

### 接入位置

建议在 paimon-plugin 内增加轻量观察入口和独立纠错入口，原聊天过滤保持原用途。

- 观察入口在可控的早期 `accept` 位置记录原消息标识、原始文本，包一层本事件的 `e.reply`，只记录回复尝试/结果，不存正文；始终不消费消息，不修改权限，不启动模型请求。
- 纠错入口安排在普通业务插件之后、派蒙聊天之前。它只看当前直接输入的命令文本，不读取历史、引用或长期记忆来触发纠错。
- 已观察到任何回复尝试时，保守跳过纠错，处理 Atlas“已发图仍放行”的情况。外部插件直接用 Bot 发送、绕开 `e.reply`，或者更早的 `accept` 已消费，观察器不能完整覆盖；对这类冲突不启用自动纠错，不能靠等待几秒推断成功。
- 初始建议与派蒙共用插件总开关、群白名单、私聊开关；命令建议是否要求点名可单独配置。建议群内以明确命令前缀为触发信号，不要求额外叫派蒙，但仍尊重框架 onlyReplyAt。

### 决策流程

1. 在框架既有转换的基础上处理首尾空白、明确的全角符号，保留游戏含义；`%` 不能纠成 `#`。
2. 按当前用户、群和已批准功能形成候选集合，识别是完整指令、缺参数、未知角色还是疑似错字。
3. 若有效命令在原插件条件下可能因数据问题失败，不再建议改写该指令。宽规则命中不能阻止合理纠错，也不能证明执行成功。
4. 优先本地别名、有限编辑距离、词序与参数校验；要支持同音误字时可增加小型拼音索引。建议先容忍一个明显错字，短命令更严格，阈值通过合成样本确定。
5. 候选唯一且差距足够时给一条正确示例；两个候选接近时给最多两项；没有把握就不打扰。不能为了覆盖率把陌生词都改成游戏角色。
6. 可选语义兜底只在本地筛出少量候选时用模型选 ID，不允许生成目录外指令。首版建议先不依赖模型做错字纠正，降低延时和费用。
7. 只提醒一次，不自动执行“猜出来的正确命令”。用户再发送正确指令时走原插件。

建议每用户每群 30 秒最多一条纠错提示，同一原消息只处理一次；数字为初始设计值，可热更新并以实际误报情况调整。UID、兑换码等参数不能用编辑距离自动修正。

## 5. 阶段二：自然语言调用

### 意图判定与当前聊天整合

普通群聊首次遵守点名 / @派蒙等触发规则，活跃窗口明确续问无需每条重新点名。2026-10-25 新增：完整、明确且当前角色已由词典唯一确认的面板请求可在窗口外独立触发，完整更新请求可独立触发或询问游戏；均遵守总开关、白名单与私聊开关。仅当前真实消息授权，不从历史补造角色。普通点名讨论不算调用申请；真实多人功能请求仍先澄清。原神/星铁的群友面板查询可从当前群昵称/QQ昵称/@解析目标，但不冒充其身份、不允许替他人更新。

完整已知面板请求由 `panel-request.js` 的有限语法和实体库解析，直接进入同一执行校验/分发分支，不请求模型或先发送聊天。其他表达使用互斥的 `answer / clarify / invoke_command` 分支，仅传入少量能力与参数约束，模型返回 ID 后再校验。无需为闲聊额外做全量指令分类，也不把416条原始声明塞进提示词。

示意：

```json
{
  "action": "invoke_command",
  "capabilityId": "genshin.profile.show",
  "args": { "character": "芙宁娜" },
  "sourceMessageKey": "程序提供的当前消息引用"
}
```

`sourceMessageKey` 只能从程序提供的当次消息集合中选择，并须与能力请求的原作者绑定；不接受模型给出的 QQ、群号、Bot 账号或权限字段。模型自报“高置信度”不能代替参数、来源和权限校验。

派蒙当前会合并不同用户消息，批次回复使用最后一条事件。**调用绝不能直接使用批次最后一条事件作为申请人。** 首版建议一个批次最多处理一个明确请求；多个用户分别请求或归属不明时拆回各自事件排队 / 澄清。会话记忆、触发前历史、引用消息、网页、知识资料、无人接话补话，都不能独立产生执行授权。

执行和普通聊天共用 session 串行调度；命令分支不再同时发一段普通聊天答复、不启动 followUp，不循环调用模型。原插件已经给出图片、文字或缺绑定提示时，直接结束本轮。必要的成功摘要可写入短期上下文，但不把任意插件输出变成长期用户记忆，不把“已请求”写成“已成功”。

### 执行方式：标准指令转交（2026-10-24 修订）

把程序白名单模板生成的标准指令交给当前框架的 `deal()`，由插件正常优先级、`accept`、规则及权限处理。既不把命令发送到群里让机器人再读，也不调用 `Bot.em`；不直接导入原插件业务函数，不按 Git 版本或文件哈希锁定插件。

1. 从真实请求者事件派生独立事件，保留本人身份、Bot/群、权限和回复通道；不沿用旧 `runtime/user`，框架重新初始化。
2. 指令来自有限模板和经过校验的参数，清空解析后的 `msg` 后交给框架解析，避免文本拼接两遍；`original_msg` 由正常预处理填入，不用原自然语言或未规范化的游戏前缀污染它。
3. 在每次调用的独立 loader 外观对象中复用原 `deal()`，使用当前优先级和规则，排除派蒙入口以防递归。不改共享 loader、插件原型或原事件。
4. 原消息已经过入站统计/冷却，转交不重复计数、扣冷却或包装原回复；重新检查黑白名单、禁言、群启用/只响应@、事件类型与规则权限。业务函数内部的账号、权限和冷却继续由它自己处理。
5. 发现同用户/群已有原插件交互上下文时，停止转交并提示先完成或退出；不能把生成指令当成另一个操作的确认或输入。新指令自身发起的后续交互仍归原插件。
6. 正常执行 `accept`、规则匹配及处理器，可使用新方法名或由另一插件接管相同指令。输出经原请求者的回复通道返回；已有回复尝试就停止后续处理，避免返回 false 后被第二个插件重复执行。
7. 追踪回复、文件/转发通道及原插件未等待的渲染 Promise。等待期间检查取消、关闭、权限及当前处理器是否仍被加载；超时不重试，已发生的请求/写入不回滚。

“无处理器”“没有回复”“原插件提示缺账号”均不假报业务成功；无回复时给出本次标准指令供手动尝试。不能自动判断同名指令的业务含义是否改变；若名称、参数或意义改变，仍需调整目录。

### 防重复、取消与结果一致性

- 使用 Bot + 会话范围 + 原用户 + 原 message ID + 能力 ID 的执行键；同一消息只允许调用一次，无消息 ID 时生成接收期唯一键。
- 合成事件加不可由用户文本控制的内部标记，派蒙路由和观察入口跳过合成调用，最大调用深度为 1。
- 首版每个明确请求最多一项能力；不允许“列出全部能力然后逐个执行”、串接命令、多步任意规划或通过定时指令转发。
- 参数仅允许已定义类型、字符长度、枚举、数值范围；角色必须解析到已知实体。10-25 已按主人授权开放原神/星铁 `panel.show` 的本群目标：程序从当前消息匹配群名片/QQ昵称或真实@，唯一确定后才向派生事件追加 at 段；模型不能输出 QQ/UID/权限。其他能力仍仅本人，目标查找失败不改查本人。
- 给每次调用设置等待期限与独立冷却，插件内真实请求不能保证可中止。超时后禁止自动重试，保留去重状态；避免第一次迟到与第二次结果重复。
- 在执行前和每次派生 `e.reply` 前检查开关、群白名单、dispose、取消代次；关闭后阻止未发送的回复。已发网络请求、已写缓存或已提交协议消息不能撤销。
- 原插件输出完整保留。默认不加“执行成功”的固定尾句；无法判断结果时记录不确定，不能由模型补写一个查询数字。
- 插件原回复不强制套派蒙长文本分段节奏，避免图片查询被拖延；同聊天发送顺序与派蒙发送时钟的整合需在桥接接口测试中明确。

## 6. 兼容边界

普通插件提交更新、内部业务实现或方法名变化不再禁用整组能力。只依赖标准指令和框架分发接口；若框架重构了这些接口，仍需调整通用桥接层。当前接口不可用则拒绝转交，不退回内部函数调用。

可用性不等于成功率：当前插件是否安装、规则是否匹配、资源/凭证/接口是否正常，依然由原插件决定。公开角色词典读取也可能因资源结构变化失效，这时拒绝猜实体，而不是解除参数校验。

## 7. 与派蒙现有能力的边界

- 默认总开关关闭，`suggest` 与 `invoke` 分开开启；目录内容不随模型输出变化。新增 JS 需要重启，纯目录配置后续可设计热更新。
- 现有 `ignoreCommandPrefixes` 继续保护普通聊天；纠错走独立路径，不能删除过滤后把所有运维指令送给聊天模型。
- 提示结构遵守 [提示词整理约定](PROMPT_REFACTOR.md)：persona 保持身份与表达，能力协议放在程序构建层，模型只在开放时看到能力清单。
- 原神查询属于现有人设范围。星铁、绝区零和点歌等若选中，可作为独立工具意图路由，先于普通闲聊的“世界外话题”策略处理；不会因此把派蒙改成万能现实知识助手。此处需与主人筛选结果一致。
- 能力调用与网页搜索是互斥中间动作：查看本人面板优先调用本地插件，不能把 UID/CK 发给公网搜索；问泛攻略若不要求图片，仍可保留普通聊天 / 知识 / 搜索路径。
- 目录提示只传功能、公开参数与必要前置条件。日志记录能力 ID、来源事件引用、耗时、状态和拒绝原因；不复制 CK、authkey 链接、原图正文或完整个人战绩到公开日志。

## 8. 建议实施顺序与验收

1. 主人先按清单编号选择“提醒 / 调用 / 不接”，并确定首批游戏范围。
2. 首批建议 6～8 个能力：原神体力、角色面板、攻略图、技能 / 命座、今日素材、日历、抽卡记录。体力、面板和抽卡属于个人查询；公开资料单独建能力。星铁 / 绝区零按所选游戏替换，不一口气开放所有项。
3. 建目录与本地纠错，用模拟注册表和回复观察验证，不安装完整 QQ/Redis 环境。
4. 验证标准指令模板和统一转交流程，保留真实请求者身份。再将结构化选择接到派蒙现有决策链，默认不开启。
5. 经明确部署授权后，在一个白名单测试群中对选中功能做真实验证，再逐项开放。只读源码核查不能代替这一步。

离线用例重点：

| 类别 | 必须验证 |
| --- | --- |
| 错字 | 单错字、同音字、缺参、全角前缀、已支持的“面版”、合法陌生指令不误报 |
