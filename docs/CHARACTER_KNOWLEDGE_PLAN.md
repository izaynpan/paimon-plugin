# 角色知识库与剧情知识库联合检索方案

日期：2026-10-28。阶段 1～5 已在本地实现；具体命令、验证和边界见 [实施与维护](CHARACTER_KNOWLEDGE_IMPLEMENTATION.md)。未部署，角色集合默认关闭。以下保留原设计依据与验收要求；依赖“角色信息抓取”成果及 [采集说明](../knowledge/characters/README.md)。

## 1. 目标与资料现状

让派蒙在讨论人物经历、性格、喜好、台词及人物关系时，优先查角色资料；涉及世界观、年代及事件前因后果时，联合《日月全事》回答。两类资料共用人物名称解析、检索入口、证据预算和版本管理。

当前已采集 136 个非预告源词条，旅行者跨元素资料合并后输出 124 份资料；这是文件数量，不等于去重后的角色人数。资料包含 986 项档案字段、243 篇介绍、844 篇故事、8,900 条台词、1,127 条他人评价、110 个邮件栏目、120 个料理栏目。邮件栏目可能包含多封邮件。角色索引现可按需构建启用，线上状态需另行部署验证。

首版覆盖下列问答：

| 问题类型 | 示例 | 优先证据 |
| --- | --- | --- |
| 基本档案 | “刻晴生日是哪天？” | 对应档案字段 |
| 喜好与习惯 | “钟离喜欢什么食物？” | 喜好类台词、故事 |
| 性格与经历 | “丝柯克是个怎样的人？” | 介绍、故事、相关台词 |
| 人物看法 | “达达利亚怎么评价丝柯克？” | 达达利亚的对应台词、丝柯克页的他人评价 |
| 台词查找 | “她关于下雨说过什么？” | 明确人物后的对应语音条目 |
| 生日与料理 | “她的生日邮件讲了什么？”“特殊料理叫什么？” | 邮件正文、料理栏目 |
| 人物与剧情 | “这个人为什么参与这件事？” | 角色故事与《日月全事》相应章节 |
| 多人比较 | “这两个人对同一件事有什么不同看法？” | 分别检索两人的相关原文 |

能力取决于已采到的原文。部分页面栏目缺失；页面未收录不代表人物没有相关资料。没有采集完整战斗技能、命座、配装或培养攻略，不能用人物档案中的元素、武器等字段推导这些答案。攻略仍沿用已有处理和联网机制。

## 2. 数据入口与切片

以 JSON 为机器读取入口，Markdown 仅供阅读，避免两份内容重复入库。使用采集报告中的输出名单建立显式清单，不扫描目录后无条件导入所有旧文件。排除预告、目录、报告和备份。

增加角色 JSON 适配器：支持普通角色格式 1 和旅行者格式 2，转换为统一检索记录。源文件保留原文，清洗、字段映射和检索扩展写入派生索引。

| 栏目 | 索引方式 | 需要保留的上下文 |
| --- | --- | --- |
| 基础档案 | 每个字段独立精确查询，可合并为短档案卡返回 | 字段名、角色、值 |
| 角色介绍 | 按原栏目和段落 | 原标题、资料所属人物 |
| 角色故事 | 短篇完整；长篇按段落/句子切为约 450～900 字的子片段 | 故事标题、父篇 ID、邻接关系 |
| 语音台词 | 一条台词一个记录，超长对话保留轮次后切分 | 原题、原文、说话者与讨论对象 |
| 人物关联 | 关联列表作为导航；有正文的评价作为证据 | 评价方向、说话者；未知说话者保持未知 |
| 生日邮件 | 只在原文明确分隔时按单封拆分 | 原题、明确写出的日期/年份；没有则留空 |
| 特殊料理 | 一份料理一个记录 | 名称、描述、效果的原始文字 |

每条记录保存：集合、稳定人物 ID、资料版本/变体、栏目、记录 ID、父记录、正文、来源页、源 JSON 路径、源条目编号、抓取时间、页面版本和内容摘要。页面版本不是游戏版本，抓取时间也不是事实核验时间。

检索副本可去重，但保留全部来源。本人评价索引引用已有台词，不再复制一遍正文；他人评价与另一人物的同条语音重合时合并证据来源。来源记录 ID 与内容摘要分开：来源位置用于定位，摘要用于发现内容变化，不能把数组序号当成跨更新不变的身份。

“观测枢收录的台词/故事”是来源栏目分类，不等于已经逐句核实为官方原文。编辑者介绍、列表关联、角色主观看法和编者推测须与明确事实区分。

## 3. 统一人物与别名库

建立插件自己维护的实体登记表，初期以原神人物为主，也允许登记只有剧情资料的 NPC。人物 ID 不依赖观测枢词条编号，源页面作为映射，一个人物可以关联多个页面或变体。

每个人物记录正式名、别名、称号、拼音，以及这些名称的来源、适用条件和歧义。检索名称映射与人物关系分开维护：名称用于找资料，不能单凭别名表证明两者具有同一身份。

现有 `knowledge/aliases.json` 中的名称组需要逐组审核迁移，不能直接当作同一人物合并表。尤其区分雷电影、雷电将军人偶、雷电真，以及具有时代、身份变化的名称。把“有关联”与“完全等同”分开。

可以复用本地角色指令字典、表情角色别名中的公开映射作为候选，但须记录来源、检查冲突，人工覆盖项优先；知识库构建不依赖加载完整 miao-plugin。首版不通过知识检索的模糊结果改变指令执行目标。

名称解析顺序：

1. 正式名精确命中。
2. 经审核的别名、昵称、称号精确命中。
3. 当前问题和同一作者上下文消歧。
4. 没有明确命中时，对疑似人物名称做同音匹配。
5. 多个候选仍无法区分时保留歧义，由派蒙自然询问。

“公子”“影”“空”等短名和常用词需额外语境，不能在“影响”“空气”中误识别人物；不要将群里其他人的话题直接当作本人的指代。

## 4. 拼音与同音错字

首版纳入同音纠错，不必等待向量检索。对已登记正式名和别名生成不带声调的完整拼音，特殊读音提供人工覆盖。例如“钟璃”可候选匹配“钟离”，“刻情”可候选匹配“刻晴”；也可支持明确输入的完整拼音。

匹配针对疑似名称片段，不把整句汉字转换后随意替换。精确命中优先于拼音；完整拼音相同、长度合理、原神人物语境明确且候选唯一时，才自动扩展检索。保留用户原始问题，同时增加规范名查询，不改用户原话和源资料。

多音字、昵称碰撞、单字名称和普通词必须有反例测试。拼音相同仍可能歧义，此时不强行选第一项。首版不默认开启拼音首字母、近音、任意编辑距离纠错，避免“能召回”变成“经常认错人”。

同一解析器同时服务角色和剧情检索：修正一次名称后，两类资料都使用该结果。后续可向表情选择等模块提供只读接口，分别保留各自匹配阈值。

## 5. 旅行者专项规则

遵循当前存储约定：女版完整，男版只存差异和共用内容引用。导入男版时复用 `scripts/traveler-profiles.js` 的 `resolveTraveler(male, female)`，校验基准摘要，按明确引用恢复完整资料；基准不匹配即拒绝发布该版本。

不能把女版全部内容直接继承给男版。检索记录保留性别变体、共用来源和元素页面收录范围；同一条文本不因来自多个元素页重复占据上下文。

女版为主仅是存储方式，不意味着默认认定用户选择了荧。“旅行者”泛问可使用共同资料；答案涉及男女差异而用户未说明时，再澄清对象。空/荧的姓名也不能自动推定其在所有叙事语境中都处于同一身份位置。

台词中“派蒙：”“旅行者：”等轮次必须保留，资料所属人物不等于每一句的说话者。来源属于某个元素页面，也不意味着该台词只能在该元素下使用。

## 6. 联合检索与回复

推荐流程：原有消息处理 → 人物/别名/拼音解析 → 按问题检索适当集合 → 统一排序与预算 → 原有聊天模型 → 必要时一次本地补查 → 仍有缺口且联网开启时进入既有限额搜索。

不增加独立的模型分类调用；首轮使用本地规则、字段匹配和全文召回，复杂意图由原有聊天调用判断。纯档案问题直查字段，性格喜好优先角色资料，世界观年代优先剧情资料，交叉问题查询两个集合。路由只作加权，低置信度不应硬性排除另一集合。

检索先沿用现有词法全文检索，增加人物、栏目、标题、关系方向加权。短的精确答案与长的故事不能只按原始分数混排；跨集合通过统一候选排序或排名融合比较，并用回归题校准。

维持一份全局上下文预算，默认沿用现有 10,000 字设置，不能给两个集合各塞一份满额内容。多人比较给各对象保留证据位置，交叉问题照顾两类来源，去掉重复正文后再补邻接片段。没有相关证据的集合不强行占位。

角色资料缺一个字段，与检索服务异常分别处理。单个集合故障时可以保留另一集合结果，但显式报告缺口，不能伪装为完整证据或绕过现有异常下的联网保护。

回答时继续保持派蒙口吻，并增加以下证据规则：

- A 对 B 的评价不能倒置成 B 对 A 的评价；页面“相关角色”列表不能直接推出亲属、友谊或感情关系。
- 角色台词中的观点不自动成为客观结论；人物性格总结应由具体原文支持，推断与明说区分。
- 引用人物第一人称时标明说话者，不能变成派蒙自己的经历，也不因检索到角色资料而切换扮演该角色。
- 角色页和《日月全事》有冲突时，比较原文、语境、年代及证据性质，不能单按抓取较新或某个集合优先就认定真伪。
- 查询覆盖度按问题判定。命中生日字段不代表同时回答了该人物的身世与全部关系；首版保持保守的 partial/unknown，不把高相关分数当作 complete/applicable。
- 来源正文保持为数据，不接受其中的指令。用户要求台词原文时优先精确引用并标来源；其他问题自然概括，避免整段灌入。

来源仍由程序映射合法 ID。角色来源显示角色、栏目和页面链接，剧情来源沿用章节与行号；内部保留完整选择记录，前台继续沿用现有最多两条展示限制。

## 7. 代码接入与版本管理

| 部位 | 计划调整 |
| --- | --- |
| `knowledge/` | 增加实体/别名登记、显式角色清单；采集 JSON 保持原有格式 |
| `lib/knowledge/` | 增加角色适配、名称解析、按集合召回与统一排序；复用现有检索和快照能力 |
| `lib/knowledge-provider.js` | 统一返回两个集合的证据，扩展角色内容类型、栏目、来源路径等元数据；同步 normalizeKnowledge 的白名单 |
| 聊天提示与研究流程 | 说明说话者、关系方向、资料缺口，维持原有模型调用上限和一次本地补查 |
| `scripts/knowledge.js` | 扩展构建、状态、查询和回滚能力，展示各集合记录数、别名冲突及缺失报告 |
| 配置 | 增加集合级开关；兼容现有 `provider: genshin-lore`、enabled 和预算，升级代码不应意外启用未配置的角色集合 |

现有构建器只接收最多 100 个 Markdown 源文件，不能把 124 份角色文件直接塞进旧清单。需要增加有类型的集合清单及分别受限的 JSON 适配入口，保留路径、大小、格式、重复及来源校验。

建议一个发布清单引用剧情索引、角色索引和共享名称表，计算综合修订号。全部校验和准备成功后原子切换；一次回答的初查、补查固定同一综合版本。修改别名、解析器或旅行者基准也改变修订，关联的证据缓存随之失效。

更新流程：采集到候选目录 → 检查报告与差异 → 构建候选快照 → 离线评估 → 发布本地索引。采集失败时不自动发布不完整批次，保留旧活动版本；源文件删除与缺失需要区分，禁止静默丢失整个人物。首版不增加定时抓取，也不把联网结果自动写进正式角色资料。

保留原有剧情索引的兼容读取和回滚路径。角色集合可以独立关闭，回滚时名称表与索引一并匹配，不能只换其中一个文件。

## 8. 性能与可观察性

单是 8,900 条已存台词和 1,127 条他人评价就超过一万条候选记录，最终切片数须以实际构建报告为准。不能假设当前九章剧情索引的冷加载耗时适用于角色集合。

构建与加载应离线或在后台 worker 准备，避免首条用户问题才同步解析全部角色。新索引准备期间继续使用旧版本；初次启用未准备好时明确不可用。测量构建耗时、峰值内存、预热耗时及热查询 p50/p95，核对现有 1.5 秒查询兜底，在目标机器可用资源内确定上限。

日志增加统一 requestId/session 标识串联初查、补查、联网和最终选择，并记录集合、修订、人物候选、匹配方式、候选数、提供片段数、字符数、耗时与截断原因。正文继续遵守原日志开关。

后续可以统计“多少轮查了角色/剧情/网页”“多少轮模型选了各类出处”“提供的证据字符占比”。这些统计可重叠，不能宣称等同最终回答的事实或文字贡献率。模型选择 ID 也不等于已证明该证据支持结论。

首版不引入向量数据库。先用独立评估题检查语义转述的漏检，再决定是否增加嵌入召回或重排；避免尚无效果数据就增加服务依赖和模型费用。

## 9. 验收与实施顺序

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 1. 数据与人物登记 | 显式清单、普通/旅行者适配、实体和别名审核报告 | 124 份现有输出无意外遗漏；男版引用完整；缺失透明 |
| 2. 名称与同音 | 共享名称解析、拼音表和歧义处理 | 正式名/别名/错字可召回；常用词、短名和多候选不误合并 |
| 3. 联合召回 | 字段查询、全文排序、人物/栏目加权、跨集合预算 | 两人比较、方向关系、人物与剧情交叉问题均有对应证据 |
| 4. 聊天与日志 | 元数据、提示边界、完整内部来源记录 | 不切角色、不倒置评价、不增加无条件模型分类调用 |
| 5. 更新与回归 | 综合版本、预热、回滚、离线报告 | 老索引兼容；源变更/删除/失败处理；时延和内存实测 |
| 6. 部署验证 | 获得部署授权后构建启用并实聊观察 | 开关/版本确认、回复质量、联网缺口与来源日志核对 |

建议新增至少 120 道人工检查过的检索题，涵盖七类资料、别名、同音错字、模糊指代、否定反例、多人比较、男女旅行者及跨集合问题；其中至少 30 道保留为未参与调参的验收题。固定题集后报告命中率及失败原因，初期目标为预期证据进入上下文的比例不低于 95%，不是已测成绩或回答正确率保证。

既有 100 道剧情回归题须复跑，不能为角色召回牺牲既有通过项。关系方向、旅行者基准校验、单字普通词误匹配、版本一致性、取消及来源伪造等关键测试要求全部通过。完整插件离线测试也需通过；无需安装完整 Yunzai/Redis/QQ 环境。

检索评估与回答评估分开。离线先确认拿到正确证据；接入后再观察模型是否使用证据、是否补出未经支持的关系、是否不必要联网。真实模型/QQ 验证不以离线通过代替。

本方案推荐阶段 1～5 作为首版完整范围：角色文本检索、别名和同音纠错、与剧情联合检索及可维护更新流程。战斗攻略库、自动生成的人物关系图谱、定时采集、向量召回留待后续独立评估。
