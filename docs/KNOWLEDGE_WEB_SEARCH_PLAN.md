# 派蒙知识库优先与按需联网方案 v1

日期：2026-10-17。状态：按本方案完成首版代码与离线验证，默认关闭，尚未部署或调用真实收费接口。下文保留设计说明；实际开关和限额以 [README](../README.md) 及默认配置为准。

目标：派蒙自动识别需要查证的问题；知识库足以回答且仍适用时不联网，只为缺失或尚未更新的部分查询网页。所有模型阶段继续使用 Flash，保留派蒙人设、现有触发与会话边界。

### 当前实现与后续知识库接口

已实现 `webSearch.enabled` 热更新开关、同次聊天动作决策、Search/Fetch、三次模型请求上限、公开资料缓存/同查询在途合并、会话证据复用、持久化每日工具请求额度、资料与引用边界及取消/降级处理。知识检索仍由 `knowledge-provider` 提供，目前默认返回 miss；没有实现向量检索、正式知识导入或后台自动同步。

`getKnowledgeContext` 可接收原来的 e/session/replyBatchMessages/participantMemories/config，另有取消 signal；补查时传入 query。返回示例（适用版本应由实际资料决定）：

```js
{
  text: "供本次问题使用的相关知识片段",
  status: "complete", // complete / partial / miss / error，必须针对本次问题判断
  freshness: "applicable", // applicable / outdated / unknown
  revision: "知识库修订号",
  currentVersion: "有依据的当前版本，未知则空",
  verifiedThroughVersion: "资料已核验的版本",
  verifiedAt: "2026-10-17T00:00:00Z",
  validFrom: "", validUntil: "", // 动态信息的有效区间
  topicType: "team",
  dependencies: ["角色A", "角色B"],
  citations: [{ id: "kb-1", title: "标题", url: "https://example.com/guide",
    publishedAt: "", verifiedThroughVersion: "", coverage: "配队、循环" }]
}
```

覆盖度和适用性由可信的本地 provider 根据检索结果和元数据生成，不接受模型自行把任意网页声明为完整知识库。完整且适用的结果阻止普通联网；显式重新联网需求可覆盖。旧 `{text,citations}` 接口保持兼容，但缺元数据不能断言时效正确。资料最多 18,000 字符，截断后降为 partial；有效期过期/尚未开始会标 outdated，畸形有效期标 unknown。检索异常或 1.5 秒超时标 error，阻止本题自动转向网页。

当前缓存统一使用可配置 TTL（默认一小时），并按 provider revision/currentVersion 失效；没有自动从正文提取活动结束时间来缩短缓存，也没有持久化维护全局当前版本表。模型获得当前日期、精确 UTC 时间与北京时间时区，仍需核对正文有效期并在预算内查证；后续知识提供器可用 validUntil 等字段给出可靠的时效状态。每轮最多携带六个网页来源及受限正文，补搜的新证据优先保留；预算计数单独落盘，不把网页写入正式知识库。

实现代码：`lib/research.js` 负责动作流程和证据，`lib/web-search.js` 负责 HTTP、限额和缓存，`lib/knowledge-provider.js` 负责知识结果归一化与超时。稳定人设不增加技术规则；联网协议仅在开关打开的聊天请求中加载。时效判断、引用支持程度和联网分类准确率仍需真实群聊检验。

## 1. 总体流程

```text
通过原有触发、白名单、防抖
  → 检索本地知识库及有效的公开资料缓存
  → 原聊天请求同时判断：是否回应、问题含义、资料是否足够
      ├─ 不需回应：正常沉默（仅原有规则允许时）
      ├─ 问题不清楚：先问清楚
      ├─ 资料足够：直接回答
      ├─ 本地检索可能漏召回：补一次本地检索
      └─ 确有资料缺口/时效缺口：申请联网
          → 程序校验开关、范围、缺口、缓存与预算
          → Search → 必要时 Fetch
          → 整理有来源的资料 → Flash 生成最终回复
          → 原有校验、分段、发送与会话处理
```

知识库优先指先使用已收录且适用的证据，不是要求网络结果永远服从旧知识。所有事实性问题先查本地；闲聊、情绪互动无需强行找资料。知识库尚未启用时，也不把每句闲聊变成联网请求。

## 2. 什么时候联网

| 场景 | 建议处理 |
|---|---|
| 闲聊、接梗、情绪、用户已提供材料的改写 | 不联网 |
| 知识库完整覆盖问题，且版本/有效期匹配 | 直接回答，不联网 |
| 已收录的稳定剧情、人物关系、未变动的技能机制 | 不因文件旧或用户说“现在”就自动联网 |
| “新角色怎么配队”，本地已有适用版本的完整配队资料 | 不联网 |
| “新角色怎么配队”，只有技能条目，没有配队或实测依据 | 先补本地检索；仍缺时只搜配队、循环或实测缺口 |
| “当前版本最佳配队”，本地配队只验证到旧版本 | 查询版本差异及新增队友/装备，不重查所有基础机制 |
| 当前卡池、活动期限、当期深渊等，已有仍在有效期内的本地资料 | 不联网 |
| 上述动态信息缺失、过期，或无法判断是否覆盖当前时间 | 联网核对 |
| “新出的那个怎么配”，无法确定角色 | 先澄清，不猜角色后搜索 |
| “我没有队友 B，能换谁”，已有适用的机制和替代资料 | 复用资料，按用户条件推导，不重复联网 |
| 稳定事实未收录，但属于明确的一般常识 | 可依模型知识简短回答；具体剧情、机制数值等缺乏可靠依据时检索查证，不靠模型自信补齐 |
| 知识库服务报错 | 标为检索失败，不等同“库里没有”；短暂重试或降级，不自动把所有请求导向网页 |
| 用户明确要求“重新联网核对” | 在提瓦特相关范围内可覆盖缓存/知识库优先策略，仍受预算和开关限制 |
| 请求无关的现实技术内容 | 保留既有人设范围，不借搜索扩大回答范围 |

“最新”不是强制联网关键词；“没有说最新”也不是不联网的依据。模型负责理解问题，程序负责执行资料状态、调用次数等约束。若要求不联网、资料又不够，说明缺口或给有限结论。

## 3. 如何判断知识库是否过时

不能仅看 Markdown 修改时间，也不能要求模型凭记忆知道最新版本。知识库检索结果需要随片段提供元数据；文件导入时间与事实核验时间分开记录。

| 元数据 | 用途 |
|---|---|
| id、主题、实体 | 定位具体角色、武器、活动及知识片段 |
| topicType | 区分稳定剧情、技能机制、配队建议、卡池/活动等 |
| source、publishedAt | 原始依据及其发布日期；未知日期保留未知 |
| verifiedAt | 最近一次核实内容仍适用的时间，重新建索引不更新它 |
| appliesToVersion / verifiedThroughVersion | 明确资料适用或已核对的版本，不把“在某版本写成”当作永久有效 |
| validFrom / validUntil | 卡池、活动等有明确时间范围的资料 |
| dependencies / revision | 配队依赖的角色、装备、反应、环境及资料修订号 |
| coverage | 能回答哪些方面：技能、配队、循环、命座、替代队友等 |

检索状态分为 complete / partial / miss / error；适用状态分为 applicable / outdated / unknown。相似度高只说明相关，不能直接判 complete。模型需指出回答各部分依赖哪些片段，完整性判断仍需真实样例评估，不承诺完全准确。

具体规则：

- 稳定剧情、已核实的基础机制不设机械的“过几天就作废”。相关官方修订或依赖改变才标记需复核。
- 配队和“最优”结论需核对阵容生态；技能没改，不代表没有新队友、新装备或新环境。不能仅用角色技能条目的日期证明最新配队已覆盖。
- 卡池/活动按有效时间区间判断；超出区间不能当作当前信息回答，即使昨天才导入。
- 对未知元数据，稳定资料可带适用边界使用；时效性问题则先核实，不直接宣称“最新”。
- 保存一个有来源与核验时间的当前版本记录。知识库同步时可更新它；没有可信记录而用户问当前版本时，按需联网核对。不能只拿本地资料的最大版本号当作线上最新版本。
- 首版不增加无人提问时的后台定时搜索；当前版本核对也计入本题的调用预算，并可复用公开缓存。

因此，一个旧文件可以仍然有效；一个刚下载的文件也可能是旧攻略。

## 4. 如何让模型决定、程序执行

第一阶段复用原聊天模型请求，不给所有闲聊额外加一次独立分类调用。它已收到用户消息、必要会话上下文、本地检索片段及元数据，可以输出以下一种动作：

| 动作 | 含义 |
|---|---|
| answer | 资料足够或无检索需求，输出最终回复 |
| clarify | 缺少决定性的用户条件，输出澄清问题 |
| skip | 符合当前群聊主动沉默规则，正常沉默 |
| lookup_local | 实体别名/问题拆分导致检索不全，补查本地一次 |
| search | 指明具体信息缺口，申请网页搜索 |

search 决策应包含：本次要回答的问题、角色/版本、missingFacts、reason、查询词、相关知识片段 ID；原因使用 missing / partial / outdated / freshness_unknown / explicit_refresh 等受限值。禁止仅返回模糊的“我想搜一下”。程序校验字段、查询长度、资料状态和额度；已判完整且适用的本地材料，不因模型随意提出搜索就发请求。模型若认为判定有误，必须指出尚未覆盖的具体事实或版本依赖。

首次本地检索可依据本批文本、已知别名及最近明确的主题完成，不必先调用模型。lookup_local 用于补偿漏召回，避免一次没搜到就断言知识库没有。它不触发付费搜索，但后续重新判断仍算一次模型调用。

中间动作不发 QQ 消息、不记录成派蒙已经说过的话、不启动无人接话计时。只在 answer / clarify / 合法 skip 时提交正常聊天结果；最终回复继续兼容 reply、emotion、可选 shouldReply/reason 和 followUp/pendingQuestion 元数据。不得把“正在查资料”当作正式回答并提前启动补话。

预算内普通直接回答通常 1 次模型调用；联网通常 2 次。补本地检索、判断来源或追加搜索可增加调用，首版建议整题最多 3 次模型请求（包含重试），达到上限时保留最后一次用于给出有边界的回答，不再递归检索。

## 5. Search / Fetch 怎么调用

继续使用现有 DeepSeek key，由插件服务器直接调用独立接口，保留 Flash 的 Chat Completions 和 JSON 输出。首版已通过 research 层实现动作校验与调度；原有旧代码不具备此能力，首次使用必须更新代码并重启，再开启 webSearch.enabled。

Search 使用 `POST https://api.deepseek.com/v1/tools/search`，Bearer 鉴权，JSON 请求。概念示例（角色与版本由实际问题填写）：

```json
{
  "query": "原神 角色A 正式服 版本V 配队 循环 替代队友",
  "count": 5,
  "need_content": true
}
```

query 最多 128 个 Unicode 字符。发送角色、版本、命座/武器等必要条件；不发送整段群聊、QQ 号或长期记忆。不默认设置 localization；ori_question 如使用，仅传筛选后的必要问题，避免夹带身份信息。

查询词按缺口生成，不把“配队、武器、圣遗物、剧情”全部搜一遍。可使用 site:/lang:/after: 等语法；after: 只在时间边界确实已知时使用，不把未知日期的有效攻略全部滤掉。检索版本未知时先核对版本，再查问题，所有请求共用预算。

先用标题、摘要、站点、日期、版本内容及重复关系筛选候选。首批以 5 条为宜，提供 2～3 个相关来源；不以搜索排序分数直接证明事实正确。优先官方机制/公告，配队建议再结合有依据的实测，多个转载不算独立交叉验证。

Search 的正文或长摘要已足够则跳过 Fetch。需要循环步骤、条件、数值或摘要缺少依据时，调用 `POST https://api.deepseek.com/v1/tools/fetch`，请求 `{"url":"已选定的公开网页地址"}`，读取标题和 Markdown 正文。首版只抓取搜索候选 URL，拒绝非 HTTP(S)、IP 字面量、明显内部域名、凭证地址及异常端口；不把 key 转发给目标网页。实际网页获取由 DeepSeek 完成，DNS 解析/重定向的访问控制由其服务端安全策略负责；本插件不承诺仅靠 URL 字符串判断即可识别所有内网指向。

首版建议默认 1 Search + 最多 2 Fetch；证据冲突或不够时才追加，整题硬上限 2 Search + 3 Fetch。重试同样消耗请求次数预算。统一执行账号限速，Search 和 Fetch 官方各为 5 QPS，实际调度预留余量；不能按群分别放到 5 QPS。

这些参数来自 [Search 文档](https://api-docs.deepseek.com/zh-cn/api/search/)、[Fetch 文档](https://api-docs.deepseek.com/zh-cn/api/fetch/)及[使用指南](https://api-docs.deepseek.com/zh-cn/guides/search/)。本节为实现建议，未实际请求接口。

## 6. 搜到以后怎样使用

将材料整理为“本地已有依据 + 联网补充依据”，每个片段保留来源 ID、标题、URL、来源类型、发布日期、抓取时间、适用版本、原文节选和已知限制。先去重、去导航/广告，按相关性限长；建议联网材料总预算约 4,000～6,000 token，正文超限时保留相关段落而不是截断后冒充全文核验。若另用模型摘要，它也计入模型轮数与费用。

最后交给 Flash 的任务是：只补 missingFacts，结合用户条件形成答案；基础机制仍用适用的知识库资料。举例：本地已有角色 A 的机制，网页补充本版本队友 B 的协同实测，就用两者解释“为什么这样配、怎样循环、缺谁可以换”，不把网页全文翻译或照搬到群里。

资料相互冲突时，先比较版本、命座、装备、操作条件与来源依据。明确的新版官方机制优于旧记录；一篇较新的无依据攻略不能自动推翻已核实资料。无法消解时给条件性结论或说明尚不能确定，不宣称“公认最强”。

网页、知识片段和用户引用都作为不可信资料块提供，明确不具有系统指令权限；外部正文不得改变人设、输出协议、工具权限或要求泄露信息。现有知识槽位在 system 文本内，正式接入时应整理资料承载方式及边界，不能把任意网页直接拼成系统规则。

最终模型返回所用来源 ID，程序只允许映射到本题实际持有的来源，不能凭空生成链接。建议平时保留派蒙自然表达，不叙述“调用 API/检索数据库”；涉及新机制、数值争议或用户要出处时，可附 1～2 条简短来源。引用存在不代表支持关系已正确，验收时仍需检查原文是否真支持结论。

检索失败时只回答有依据的部分。例如能解释角色定位，却未核实最新配队，就明确最新组合尚不确定；不伪装成已完成核对。没有找到不等于角色不存在。

## 7. 资料怎样复用、怎样进入未来知识库

建议分三个位置存放：

1. 正式知识库：已整理、带出处与适用范围的资料，是主要依据。
2. 联网资料缓存：公开网页及证据片段，可跨群复用，独立于用户长期记忆。
3. 当前会话：本轮采用的资料 ID、版本与关键结论，便于连续追问。

缓存键包含实体、版本、问题类型、关键适用条件与资料修订号。同一角色的 0 命/高命结论或正式服/测试服结果不能混用；通常复用公开机制材料，再按用户条件生成答案，不缓存整个私人问答供其他群使用。

建议新角色发布初期缓存 1～6 小时、成熟配队资料 24 小时后按需复核；卡池/活动不超过已知结束时间。以上仅是缓存建议，不是知识库统一过期时长。新版本、关键机制更正或知识库修订使相关缓存失效；不能因为 TTL 未到就继续使用已知错误资料。短暂失败/空结果可缓存 1～5 分钟，避免连续重试。

正式知识库刷新后，优先回到正式知识库。网页结果不自动覆盖原知识、不写入用户长期记忆；首版只保存待整理线索，后续另设计经过核验的导入流程。可记录“哪些主题经常因缺失或过时而联网”，指导更新知识库。

## 8. 与现有功能的边界

- 只在现有插件已接纳的消息范围内工作，不监控未触发群，不扩大白名单或世界外话题范围。skip 仅沿用现有选择性回复规则。
- 整个检索和回答任务进入原 session 串行队列；不同群共享搜索限速和公开资料缓存，不共享私聊上下文。
- 每次外部调用前、发送前复查开关、白名单、key 及会话状态；已有 API 请求或协议消息不能声称已撤回。搜索等待期间收到正常追问沿用入队机制；明确停止、关闭功能等则终止后续处理。
- 知识获取目前在聊天 try 块前，正式接入需对检索异常做明确兜底。检索失败不影响其他聊天；没有必要为此修改框架。
- 建议整题联网阶段共享 15 秒预算，包含重试、搜索与抓取；这是应用主动超时，不是服务端延时承诺，不包含最终模型生成与 QQ 发送等待。最终模型沿用原模型超时策略；搜索超时后不再等待迟到结果或发第二份答案。
- 原回复节奏保持；慢搜索会使实际首条延迟增加。只在最终文字成功后更新正常回复记录与补话计时。
- 记忆评估和主动补话默认不联网；评估材料不包含原始网页或中间规划，仅保留正常聊天所需内容，避免把攻略结论误写成用户特征。
- 功能默认关闭；新增 JS 需要部署并重启，后续配置可热更新，不能靠现有空知识库接口自动获得功能。

## 9. 用量、日志与验收

不开启无限搜索。每题限制 Search/Fetch 次数、模型调用次数、资料长度与总等待；另设每日请求额度/费用预算，额度不足时保留可靠内容并说明未知。请求费与 token 费分开统计，缓存命中不能当成零模型费用。

记录决策原因、知识库 revision/状态、使用片段 ID、缺口类型、公开资料缓存命中、Search/Fetch 次数/结果、模型 usage 与耗时。用户文本、查询词和模型正文遵循日志开关与脱敏规则，key 永不写日志。统计回答涉及联网的比例，以及因知识库缺失/过时联网的主题，不以总群消息数估算 API 量。

最低验收样例：

| 用例 | 应观察到的行为 |
|---|---|
| 本地完整的稳定剧情资料 | 0 Search、0 Fetch |
| 已核验当前版本的新角色配队 | 0 Search、0 Fetch |
| 只有机制，没有配队资料 | 补本地检索后仍缺，才联网 |
| 上版本“最优队”，当前新增相关队友 | 仅查差异，不把旧最优当最新 |
| 缺元数据的旧剧情 / 当前卡池 | 前者不机械过期，后者核实适用日期 |
| 当前版本记录未知 | 不把知识库最新版本号当线上版本号 |
| 知识库异常 | 不伪装 miss，不导致所有消息联网 |
| 用户连续问替代队友 | 复用已有适用材料，新增缺口才搜索 |
| 群里旁人聊天、要求安静 | 遵循原决策，无不必要联网 |
| 多个群同时问同一公开主题 | 可合并在途公共查询、复用结果，独立生成回复 |
| 网页带恶意指令、版本混杂或来源冲突 | 不执行网页指令、不泄露数据，保留事实边界 |
| 超时、关功能、移出白名单、停止插件 | 无迟到发送、无无限重试、不破坏其他会话 |
| 最终回复附来源 | 链接来自本题有效来源，原文支持对应结论 |

离线测试覆盖调用门槛、预算、缓存失效、取消和响应解析；真实模型评估另检查“知识库已覆盖却仍联网”和“资料已过时却不联网”的误判率。不能用单元测试通过代替语义效果验证。

首版已按“知识结果协议 → 聊天动作 → Search/Fetch 与缓存”完成实现。未来接真实知识库时替换知识提供器，不重写整套聊天流程；仍需结合实际资料形态细化时效判断。当前没有选择向量库、启动后台抓取或改动个人运行配置。
