# paimon-plugin

基于 DeepSeek deepseek-flash 的 QQ 对话插件。插件不修改 Miao-Yunzai 框架文件，支持群级连续会话、私聊会话、按 QQ 用户保存的长期记忆、自然分段回复和可选表情包。

## 使用前准备

1. 在项目根目录安装现有依赖：

   ~~~sh
   pnpm i
   ~~~

2. 推荐通过环境变量提供 DeepSeek API key。PowerShell 示例：

   ~~~powershell
   $env:DEEPSEEK_API_KEY = "sk-..."
   node . dev
   ~~~

   也可以在 config/config.yaml 中覆盖 deepseek.apiKey，但不要把包含真实密钥的配置提交到版本库。

3. 修改配置后无需重启插件；config 目录会被监听并自动重载。

DeepSeek 请求固定使用 OpenAI 兼容的 POST /chat/completions：默认模型为 deepseek-flash，非流式，显式关闭思考模式，并开启 JSON Output。聊天和 session 记忆评估都会要求模型返回合法 JSON。

## 自动搜索与知识库优先（2026-10-17）

新增功能默认关闭。更新代码并重启 Yunzai 后，在个人 `config/config.yaml` 顶层加入：

~~~yaml
webSearch:
  enabled: true
~~~

设为 false 关闭，后续开关支持热更新。无需开启长期记忆或群聊主动沉默；知识库尚未建设时也能使用搜索。只访问 DeepSeek 官方 Search/Fetch，默认复用 `deepseek.apiKey`，需要可直接调用官方接口的 key；不会把搜索请求发到自定义模型代理。当前未执行真实收费 API 或 QQ 联调。

需要分开使用密钥时，在个人配置中设置 `webSearch.apiKey`。它只用于 Search/Fetch，聊天判断、最终回复、记忆评估和补话仍使用原聊天 Key。省略、留空或仅有空白时沿用聊天 Key（包括其环境变量优先解析结果）；填写后优先使用搜索专用 Key，即使鉴权失败也不会改用聊天 Key 发起搜索。搜索 Key 支持配置热更新，更换实际生效的搜索 Key 会取消在途研究任务；已发出的请求无法撤回。真实 Key 只放在被忽略的个人配置中。独立 Key 隔离的是工具调用费用，阅读搜索资料增加的模型 token 仍计入聊天 Key；每日工具额度仍按整个插件累计，换 Key 不重置。

完整可选配置如下；已有同名分组时合并字段，不重复创建分组：

~~~yaml
webSearch:
  enabled: true
  apiKey: ""              # 可填写搜索/抓取专用 Key；空字符串沿用聊天 Key
  maxSearches: 2           # 每个聊天批次最多搜索 2 次，允许 0～2
  maxFetches: 3            # 每批最多读取 3 页，允许 0～3
  timeoutMs: 15000         # 从首次搜索起共用时限，范围 1000～30000 ms
  dailyRequestLimit: 200   # 每天 Search + Fetch 的请求尝试总额，0 禁止新请求
  cacheTtlMs: 3600000      # 公开资料内存缓存 1 小时；0 关闭复用，最多 24 小时
  maxContextChars: 12000   # 网页正文传给模型的合计字符预算，1000～24000；不是 token 数
  includeSources: false   # true 时按模型选择附最多两个经程序映射的来源链接
~~~

- 先查知识接口，再在原聊天请求中决定直接回答、澄清、合法沉默、补查本地或联网；普通回复不额外加独立分类调用。每题最多 3 次模型请求，开启搜索的聊天请求不自动重试，工具请求也不自动重试。中间动作不发消息、不写成已回复上下文、不启动无人接话补话。
- 搜索由模型理解语义触发，不要求用户说“搜索”。知识库返回完整且适用时由程序阻止普通搜索；只有明确要求重新联网核对才可覆盖。库内有旧技能条目不等于已有最新配队资料。知识库失败单独处理，不自动当作缺失并联网。
- 2026-10-18 完善搜索/澄清边界：当前或近期消息已有具体名字和提瓦特攻略问题时，模型不认识对象、缺元素/技能/定位/登场版本属于公开知识缺口，应在允许检索且资料不足时按原名先查；疑似错字/别名也先核实，不擅自替换角色。只有无上下文的含糊指代、不可公开查询的个人条件，或查后仍无法确认身份时才澄清。续话补充“新版本”等信息后承接前文对象，不反复索要公开资料。搜索不能证明角色存在，无结果也不能证明不存在。该边界由提示引导，未用角色名单或关键词强制联网，真实模型漏搜率仍待实测。
- 首次取 5 条候选，最多选 3 个来源；Search 有正文就不重复 Fetch。概述类长摘要（至少 600 字符）可直接使用；模型要求细节或摘要不足时尝试抓取前两个候选，仍受整题总额约束。网页长度、响应体大小、查询词和公开 URL 有限制，摘要和原文会明确区分。
- 公共查询/抓取结果按 key、知识修订号、已知版本及查询内容隔离缓存；同查询可合并在途请求，等待者取消不影响仍有效的其他调用。缓存命中不会更新真实获取时间，空结果最多缓存 1 分钟。会话内可复用仍有效的证据，换知识修订/版本或过期后失效。尚未从网络自动维护结构化版本清单，当前版本不明时由模型在同一预算内查证。
- 每日额度按北京时间日期计算，在插件 `data/runtime/web-search-budget.json` 中持久化；重启不清零。包含失败、超时、可能已发出但未收到结果的尝试，属于保守额度，不是官方账单；模型 token 另计。200 次工具尝试对应按 0.005 元/次估算至多约 1 元工具请求费/日，不限制聊天 token 开销。预算读写异常时不发新工具请求；单进程保证，并行运行多个机器人进程不能共用此文件当分布式配额。
- 关闭开关、插件、移出白名单、去掉/更换 key 或 dispose 时取消当前研究任务；最终发送前仍复查。已发 API/QQ 消息不能撤回。数值配置对后续批次生效，在途任务沿用原预算快照。私聊或明确点名/@派蒙的停止查询请求可取消正在研究的任务；普通续话仍按原队列处理。
- 15 秒时限包含搜索/抓取排队、网络和两次搜索间的判断耗时，不包含最终模型生成和 QQ 回复节奏等待。超时/无结果/额度不足时使用已有依据并说明未知，不能伪装已核实最新内容。没有官方延时保证。
- 网页原文仅作为独立语境数据，不能改变人设、协议或工具权限；正文不写入用户长期记忆或自动覆盖正式知识库。记忆评估与无人接话补话不联网。模型语义判断和资料真实性仍需实群验证。
- 日志新增 `search_decision`、`search_summary`，记录状态、次数、缓存、错误代码、模型轮次和耗时，不记录查询或网页正文；模型请求/响应中的这些正文仍遵循原 `includePrompt/includeResponse` 开关。模型日志 `researchRound` 区分多阶段请求。
- `search_decision` 也记录最终 answer/clarify/skip、是否显式返回动作 `actionExplicit`、知识状态/来源数量；clarifyReason 只接收有限分类（指代不明、个人条件、查后身份未确认、检索不可用），缺失或非法值记 unspecified。保留旧回复格式兼容，不因缺 action 自动追加模型调用。下次实测同时检查动作是否触发及搜索专用 Key 的接口结果，本次未发起真实收费请求。

知识库当前仍为空实现；已接入可扩展的覆盖度/适用性协议，并不代表已实现 RAG 或自动导入资料。接口与设计见 [知识库优先与按需联网](docs/KNOWLEDGE_WEB_SEARCH_PLAN.md)。

## 人设与提示词维护

`config/persona.md` 负责稳定的身份、性格、知识边界和表达习惯；`lib/prompt-builder.js` 负责 JSON 协议、是否回应、补话状态及当前称呼配置。功能规则按开关加载，不应把程序字段和开关说明重复写进人设。2026-10-16 已完成合并整理，需求保留清单、体积对比与待实测场景见 [提示词整理对照](docs/PROMPT_REFACTOR.md)。

人设/配置支持热重载；更新 `.js` 需要重启。若通过 `persona.file` 使用自定义人设，本次默认人设整理不会替换它，需要按需合并。离线测试仅验证提示内容和代码行为，不代表真实模型回答质量已经提高。

## 触发与会话

conversation.useUserNickname 默认 true，让派蒙特指用户时优先称呼群名片；在 config/config.yaml 的 conversation 分组中设为 false，则默认称呼“旅行者”。已有个人配置中显式设置的 false 仍会覆盖新默认值，需要改为 true 或删除该覆盖项才会开启。群聊和私聊均生效，支持热重载，从后续模型请求开始使用。称呼优先取协议提供的群名片，缺失或仅含空白时使用 QQ 昵称，再缺失则回退为“旅行者”；私聊没有群名片时直接使用 QQ 昵称，不会使用 QQ 号作为称呼。群内各用户分别对应自己的称呼，不影响会话或记忆标识。这通过模型提示引导，避免对回复文本做全局名字替换。

~~~yaml
conversation:
  useUserNickname: true
~~~

trigger.nicknames 中的称谓会自动加入聊天系统提示，告诉模型这些称谓指向派蒙；persona.md 定义如何结合上下文理解称谓变化并自然回应。建议保持 trigger.stripTriggerName: false，让模型看见用户原始称呼。陌生昵称可由模型结合上下文理解，但未配置的昵称本身不会触发群聊。

群白名单默认关闭。要限制为仅指定群可用，在 config/config.yaml 中加入（支持热重载）：

~~~yaml
groupWhitelist:
  enabled: true
  groups: ["123456789", "987654321"]
~~~

开启后，空列表禁止所有群；未列出的群不会触发、收集消息或调用模型，私聊仍按原配置处理。移出白名单后，待处理批次和后续发送会被拦截，结束时不再评估记忆；已发出的模型请求无法撤回。已发送的消息和已有记忆不会删除。

- 私聊：未被更高优先级插件处理的非指令文本会触发。
- 群聊初次触发：at 机器人，或文本任意位置包含 trigger.nicknames 中的昵称。
- 群聊触发后：同一群进入活跃 session，后续未被其他插件捕获的非指令文本都会进入该 session。
- #、＃、*、% 开头的消息始终忽略，不创建、保存或刷新 session。
- 只处理文本；图片、语音、视频和文件不会进入会话。
- 同一 session 先等待 conversation.debounceMs，把连续消息合并成一次回复；机器人回复完成后保持 conversation.activeWindowMs 的活跃窗口，默认 90000 毫秒（90 秒）。已有 config/config.yaml 中的同名设置会覆盖此默认值。
- 同一 session 同时只会执行一个聊天 API 请求，回复期间的新消息进入下一批。
- 首条也参与节奏控制；同一群聊/私聊的消息跨 API 批次统一计时，间隔同时考虑上一条阅读时间和下一条长度，目标默认 4～24 秒，每轮有 ±10% 节奏变化。不再用整轮预算压缩间隔。
- 攻略问答默认将首条及分段目标等待减半（`reply.guideDelayScale: 0.5`），日常聊天保持原节奏。分类由原聊天请求同时返回，不额外调用模型，与是否联网或命中知识库无关；详见下方回复节奏。

### 先发内容，再呼唤派蒙

2026-10-13 已改为触发时按需查询协议历史，不再持续缓存未触发的群消息。例如先发“蒙德有什么好吃的”，随后只发“派蒙”或单独 @Bot，会尝试补入前文一起交给模型。当前仅启用已核对的 TRSS OneBotv11 + NapCat 接口组合；其他协议或能力不匹配时跳过补查，不影响正常呼唤。

~~~yaml
conversation:
  preTrigger:
    enabled: true
    windowMs: 30000
    maxMessages: 3
    historyPageSize: 20
    historyMaxPages: 3
    historyTimeoutMs: 1500
~~~

- 仅在没有活跃或仍在收尾的 session 时，通过昵称/@ 明确触发补查。以本次呼唤的消息 ID 与时间定位，同群、同一用户、此前 30 秒内最多 3 条文本；锚点、重复项及呼唤之后的消息不补入。已有活跃会话和私聊保持原逻辑。
- 默认每页 20 条、最多 3 页，共用 1500ms 总预算；到达时间边界、取够文本或游标不前进即停止。忙碌群不保证覆盖完整 30 秒。上限：时间窗 5 分钟、选取 20 条、每条 4000 字符、每页 100 条、5 页、总超时 5 秒。任一数量/时限设为 0 可禁用补查。
- 查询沿用本次事件的 Bot 连接，但会话仍按群隔离，不增加 Bot 账号白名单。安全传输只发送 get_group_msg_history，使用独立 echo 等待项与可取消计时，不调用超时会关闭共享连接的框架 sendApi/getChatHistory；不依赖 WebUI 登录或新增协议端口。
- 超时、断线、无接口、缺少锚点/时间、错误或不可信顺序均放弃补充，只正常处理本次呼唤；不在群里提示查询失败，不退回常驻文本缓存。等待期间同群消息暂存至初始化队列，最多 50 条；满额时取消查询、先处理已接纳消息再继续。全局最多 8 群并行补查，满额的其他群直接正常触发。
- 白名单、指令、自身过滤及昵称/@ 开关仍有效；单独 @Bot 需开启 trigger.groupMentionTrigger。历史仅解析结构化文本和 @ 段，跳过 CQ 字符串、纯图片/语音/文件，不增加读图能力。
- 历史可能包含此前被其他插件处理过的普通文本，无法重建其消费状态；只作为语境，不重放事件或执行指令。不会向模型提交原始整页历史，只提交最终筛选文本。
- 未触发时不建立 session、不查询、不缓存文本、不写插件日志或长期记忆。补入后按正常批次的模型日志和记忆开关处理，仍不需要开启知识库或长期记忆。history_lookup 日志仅记录状态/原因/页数/数量/耗时；模型请求中的正文遵循 includePrompt，协议框架自身的日志配置独立。
- enabled=false 可关闭；配置热更新作用于后续处理，合并前复查白名单、开关和状态，迟到结果丢弃。移除的是前置文本缓存，不是正常活跃会话的内存上下文。代码更新需要重启，真实群聊端到端效果仍待部署后验证。

### 群聊适时不回复（可选）

默认关闭以保持原行为。安装新代码并重启后，在已有 config/config.yaml 的 conversation 分组内设置：

~~~yaml
conversation:
  selectiveGroupReply: true
~~~

此开关仅影响群聊，后续请求支持热更新；私聊仍按原逻辑。白名单、指令过滤、初始昵称/@ 触发设置都不变，窗口外普通发言仍不会调用模型。

- 同一次聊天请求判断整个防抖批次是否需要回应，不额外调用分类 API；主动不回复仍有判断请求的 API 开销。
- 模型同时得到发言者、是否 @Bot、@其他人的列表和匹配称谓。@别人只是线索，不会一律跳过；混合批次应只回应对派蒙说话的部分。
- 开启时输出格式为 `{"shouldReply":true,"reason":"direct_address","reply":"你好","emotion":"happy"}`。不回复为 `{"shouldReply":false,"reason":"talking_to_others","reply":"","emotion":"neutral"}`。
- 回复原因允许 direct_address / answering_paimon / relevant_followup；不回复原因允许 talking_to_others / no_response_needed / asked_to_stop。明确合法的 false 才是主动沉默，空响应、缺字段、类型错误及矛盾字段仍走错误处理，不算正常跳过。
- 主动沉默不发文字、不发表情。日志新增 reply_skipped，包含 session、批次编号、原因代码及 decisionSource=model，不记录额外消息正文；可与 reply_sent 的失败状态及 API 错误日志区分。触发前被过滤的消息不会生成 reply_skipped。
- 沉默批次保留在本次会话短期上下文，标注未回复且不代表同意；长期记忆评估排除这些批次及仅参与沉默批次的用户，全程沉默不调用记忆评估。
- 开启时，实际文字回复发送完成或模型作出合法沉默决定后，都会从处理完成时重新计时 90 秒（2026-10-12 调整）。沉默只刷新窗口，不更新实际回复时间 lastReplyAt；没有成功发送的异常不续窗口。
- 连续消息即使都判为不回复，也能持续保活，让后续不带名字的“可以说啦”进入模型判断，并保留本次会话最近上下文。持续群聊因此可能延长 API 调用时间、增加费用；这不启用长期记忆，也不保证模型每次都正确理解恢复意图。
- 到截止时间不再接收无触发的普通续话，防抖也不能无限推迟判断；截止前已入队/在途的批次允许串行处理完成。若最终回复成功或合法沉默，再开启完整窗口；无成功发送且不是合法沉默则到期收尾。处理期间再次明确触发可重新开启窗口，不并发调用。
- 开关按请求快照解释响应，热切换不撤销在途请求；窗口参数对已设定的截止时间不追溯调整。

开启后也会提示模型结合上下文识别昵称嵌入、谐音、双关或故意断句：明显在逗派蒙时可以简短接梗，无需明确提问；偶然包含昵称或旁人交流仍可保持沉默，不强行猜梗，也不因此展开世界外知识问答。这只是同次请求里的通用提示，不增加分类请求或针对某句的特判；原有触发边界不变。

这是模型判断，不保证每条消息都分类正确；离线测试验证协议、计时及发送行为，实际语义效果仍需群聊观察。异常时可能按原错误策略发送兜底提示，不等于主动沉默。

### 询问无人接话时的主动补话

默认关闭；需要时在已有 conversation 分组中加入：

~~~yaml
conversation:
  unansweredFollowUp:
    enabled: true
    waitMs: 30000
    cooldownMs: 180000
~~~

- 正常聊天的同次 API 额外判断：派蒙是否提出了真正期待回答的问题，以及上一个问题是否已被接住。不是遇到问号就触发，反问、自问自答、礼貌收尾及要求安静后的回复不应建立等待。不依赖长期记忆，也不要求开启 selectiveGroupReply，私聊同样支持。
- 只在这一轮文字全部发送成功后建立等待，以最后一段文字成功时间为起点。每个聊天最多等待一个问题；发送期间到达的用户消息仍进入下一批，对新问题作判断。
- 回答、代答、接梗、拒绝、要求停止、被问者转移话题均可结束等待；只有明确判定为无关且派蒙正常保持沉默时保留原倒计时，不因旁人聊天重置。无法确定、缺失/无效元数据时保守取消；派蒙已开始另一段正常发言也会撤销旧问题。未开主动沉默时，正常回复仍按原规则进行，因此无关消息若引发派蒙发言，也会撤销旧问题。
- 默认 30 秒到点后，最多额外调用一次聊天 API，综合问题、对象、提问后消息决定补一句还是保持安静。补话通常 10～35 字；代码限制为一条非空单行文本、最多 80 个 Unicode 码点，不附表情包，不创建下一轮自动补话。不是固定话术，也不保证每个问题都补话。
- 到点有普通消息待处理时先让用户消息走完；最多宽限 30 秒，之后放弃。补话请求和正常聊天使用同一 session 串行队列；不同聊天不互相阻塞。补话 API 最长 15 秒且不重试，失败或无效输出安静结束，不发错误兜底。请求或节奏等待期间收到新的已接纳文本，会丢弃这次补话；已发到协议的消息无法撤回。
- 发送复用连续消息节奏，不再计算一份用户新提问的首条反应等待。补话发送只尝试一次；成功后同一聊天默认 3 分钟不能再建立补话，正常回复不受此冷却影响。这个冷却不是此前关闭的群聊/个人普通回复冷却。
- 仅在原 session 仍有效时执行，不自动复活已结束的会话。成功补话会作为机器人发言加入短期上下文并续原活跃窗口；不伪造用户消息，主动补话批次排除长期记忆评估。仅维护内存中的问题、事件引用和定时器，重启不恢复。
- 关闭功能/插件、移出白名单、移除 key、会话结束或停止插件会取消等待；请求前及发送前重新核对，已发 API 不能撤销。waitMs 热修改按原成功发送时间重新计算，不按最近无关消息重置；范围 5 秒～5 分钟，cooldownMs 范围 30 秒～1 小时，非数值回退默认。已经开始的请求不因修改等待时长重排；冷却使用成功发送时的配置。
- 只判断实际到达本插件并被接纳的文本；被框架/其他插件拦截的消息及图片语音不保证可感知。是否真正在等回答、是否相关属于模型判断，仍需实群观察误判率。

日志新增 follow_up_armed、follow_up_not_armed、follow_up_cancelled、follow_up_due、follow_up_decision、follow_up_sent、follow_up_error，包含问题 ID 和原因，不写问题正文；API 日志及 reply_sent 用 type=unanswered_follow_up 标记，正文仍遵循现有日志开关。可据此判断是没有资格、冷却、用户已接话、模型选择不打扰，还是调用失败。

新增代码需要更新后重启 Yunzai。之后开关和数值支持热重载；本功能目前完成离线验证，尚未部署或验证真实模型效果。

### 回复节奏

2026-10-18 新增攻略问答加速：模型在最终回复 JSON 中给出 `replyKind: guide/chat`，根据本轮主要目的区分攻略与日常聊天。配队、培养、武器/圣遗物、机制/循环、资源路线、深渊、抽取建议和版本/活动实用问答，以及相关追问/必要澄清属于 guide；角色/剧情闲谈、情绪交流及仅提及角色名字仍属 chat。无需实际联网，无额外分类 API；缺失/非法分类按 chat 兼容旧格式，真实分类效果仍待实测。沉默、主动补话与程序错误兜底沿用原处理。

`reply.guideDelayScale` 默认 0.5，范围 0.1～1；设为 1 恢复普通节奏。先按原公式、抖动和上下限算出目标，再乘倍率，所以首条反应目标、跨条阅读/输入目标和同批表情等待同步减半：默认目标范围由 4～24 秒变为 2～12 秒。忽略抖动时，等长 20／40／60 字的目标从 8／14.8／21.6 秒变为 4／7.4／10.8 秒；个人配置的原延时参数也按倍率生效。切回闲聊恢复倍率 1，共用成功发送时钟，不改变拆句、条数或内容。

倍率缩短的是人为等待目标，不是端到端耗时或剩余等待直接减半；防抖、API/搜索及排队已耗时间仍抵扣目标，只补不足部分。该功能可缩短长攻略占用队列的时间，但不取消已开始的旧回复、不合并或去重重复追问。更新 JS 需重启，之后倍率支持热更新，在途批次沿用自身配置快照。

目标间隔公式（毫秒）：max(baseDelayMs + 下一条字数 × typingMsPerChar, 上一条字数 × readingMsPerChar)。按实际发送消息的 Unicode 码点计数，随后应用整轮共用的随机系数并限制到 minDelayMs/maxDelayMs。按同一群号或私聊用户共用成功发送时钟，不按 Bot 账号、API 批次或拆句边界重置。

每批首条同时满足两个期限：①本批最后一条用户消息进入插件缓冲区的时间 + 首条反应时间（baseDelayMs + 首条字数 × typingMsPerChar，同样应用抖动与上下限）；②上一条成功发送完成时间 + 连续消息目标间隔。取较晚期限，只补等不足部分，不把两份等待相加。无上一条记录时仅按首条反应时间计时；后续分段只遵循连续消息间隔。用户在提问之前思考、打字的时间不会抵扣新一批的首条反应时间。防抖、API 和排队耗时仍计入；它们过慢时实际间隔可能更长，maxDelayMs 不是端到端延时上限。单条回复、关闭拆分及代码块等结构保护内容都适用。

升级旧版本时，在已有 config/config.yaml 的 reply 分组中调整以下字段（不要重复添加 reply 分组）；旧的 typingMsPerChar: 90、readingMsPerChar: 120、maxDelayMs: 8000 等用户设置仍会覆盖新默认值，也可删除这些覆盖项。旧 maxTotalDelayMs（包括服务器原有的 30000）已忽略，可删除；不再为赶整轮预算而加速。此次涉及 JS 代码，更新后需要重启 Yunzai；后续调整这些数值仍支持配置热更新，在途批次使用原配置快照。

~~~yaml
reply:
  split: true
  guideDelayScale: 0.5     # 攻略目标等待倍率；1 恢复普通节奏，范围 0.1～1
  minDelayMs: 4000
  maxDelayMs: 24000
  baseDelayMs: 1200
  typingMsPerChar: 340
  readingMsPerChar: 360
  delayJitter: 0.1
  minSegmentLength: 6
  maxSegmentLength: 180
  keepCodeBlockTogether: true
  sendRetries: 1
~~~

普通聊天保留 4 秒下限。忽略随机抖动、且内容及时准备好时，前后条均为 5／20／40／60 字的连续消息目标间隔分别为 4／8／14.8／21.6 秒；每批首条按自身长度计算的反应时间也使用这些目标值，上一条较长时可能还需满足更晚的阅读期限。攻略问答另乘上述倍率。较长回复的整轮发送时间和后续批次排队时间会增加，不设整轮等待上限，也不丢弃后续内容。

表情包与错误兜底共用该时钟；表情包按 0 字计入，普通聊天默认至少隔 4 秒，攻略批次同样应用倍率，前文较长时按阅读目标等待。合法沉默和发送失败不更新成功发送记录；等待后重新检查插件开关和群白名单，停止插件时取消等待。时钟只保存发送时间和长度，不保存聊天正文；短期 session 切换仍保留，空闲至少 5 分钟后自动清理（较大的间隔配置会延长保留时间），进程重启后重新计时。其他插件的发言不纳入此时钟。

回复不再限制条数，旧配置中的 maxSegments 会被忽略，可删除。人设建议闲聊回应一个重点、说完即止，攻略以信息完整为先，不设每段固定字数或段数。默认 minSegmentLength 从 15 改为 6（含标点、按 Unicode 码点计数），个人配置已有的 15 仍会覆盖此默认值。感叹号 ！/! 保留并参与拆句，但不是强制边界，过短的同类片段仍会合并；例如“最喜欢吃啥……这可太难选了！”后接足够长的说明时会独立成条，“太香了！”等短句仍可合并。显式换行保留为分段边界；说明后的问句另起一条，连续问句在 maxSegmentLength 范围内合并。普通短句合并时保留内部标点，只在最终分段完成后去掉消息最末尾的中文句号。规则按标点和换行判断，不是额外调用模型做语义分析。

超长普通文本仍按 maxSegmentLength 拆分；开启结构保护时，代码块、JSON 和列表整体发送。消息再多也不会压缩目标间隔。聊天过程中不会模拟协议的“正在输入”。

框架限制：如果群配置启用了严格的 onlyReplyAt，非 at 消息可能在到达本插件前被框架过滤。需要把派蒙昵称同步加入群配置 botAlias，或保持 onlyReplyAt: 0。

## DeepSeek 调试日志

默认开启 JSONL 调试日志：

~~~text
data/logs/deepseek.jsonl
~~~

Arch Linux 上可以实时查看：

~~~sh
tail -f plugins/paimon-plugin/data/logs/deepseek.jsonl
~~~

每行是一个独立 JSON 事件，主要事件类型：

- model_request：模型类型、session 标识、完整 messages 和请求参数。
- model_response：模型原始 content、解析后 data、耗时、尝试次数、finish reason 和 token usage。
- model_retry / model_error：重试或最终失败的状态码、错误码与耗时。
- reply_sent：最终回复文本、情绪标签、实际成功发送的分段以及是否失败。pacing 数组包含 kind、length、previousLength、targetGapMs（连续消息目标间隔）、waitMs（补等时间）、previousSentAt/sentAt（毫秒时间戳）、actualGapMs（跨条实际间隔）和 success。新增 isBatchFirst、reactionStartedAt（本批最后一条用户消息接收时间）、reactionTargetMs（首条反应时间目标）；firstLatencyMs 现在记录每批首条相对该接收时间的耗时，不再仅在没有上一条发言时记录。后续消息的首条相关时间字段为 null，失败发送的 sentAt 为 null。实际时间以协议成功返回为准，无法测量 QQ 客户端真正显示的时刻。pacing 不含正文，关闭 includeResponse 后仍可检查节奏。
- memory_applied / memory_failed：session 记忆评估最终是否写入用户记忆。

API key 和 Authorization 会被自动脱敏，不写入日志。完整 prompt 和回复可能包含聊天与用户记忆，调试完成后可在 config/config.yaml 中关闭或隐藏正文：

~~~yaml
logging:
  enabled: false
  # 或保留事件但隐藏正文：
  includePrompt: false
  includeResponse: false
  includeUsage: true
~~~

日志默认达到 5 MiB 后轮转，最多保留 3 个文件，可通过 logging.maxBytes 和 logging.maxFiles 调整。

## 用户记忆

长期记忆按 QQ 用户保存：

~~~text
data/memory/users/<user_id>.json
~~~

完整 session 结束后，插件单独调用一次 deepseek-flash 做记忆评估。模型只能更新当前参与用户；程序会校验用户 ID、返回结构和新记忆，并通过用户级 Promise 队列与临时文件 rename 避免并发覆盖或半写入。

评估失败时旧记忆保持不变，session、旧记忆和错误摘要会写入：

~~~text
data/runtime/failed-memory-evaluations/<session_id>.json
~~~

失败材料数量由 runtime.maxFailedMemoryEvaluationFiles 限制。这些运行数据已在插件 .gitignore 中排除。

## 表情包

把图片放在 data/stickers 下，并在 config/stickers.yaml 中按情绪填写相对于插件根目录的路径：

~~~yaml
happy:
  - data/stickers/happy/001.jpg
comfort:
  - data/stickers/comfort/001.jpg
~~~

只有模型返回匹配情绪、配置启用且概率命中时才发送。路径被限制在插件目录内；表情包失败不会影响文字回复或记忆更新。
